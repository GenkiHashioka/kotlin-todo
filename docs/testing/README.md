# テスト実施結果（testing）

レビューしたテスト設計に対し、どの環境で何を実行し、どうなったかを記録する。予定の手順・期待結果は[test-plans](../test-plans/README.md)、実施後の学び・判断は[journal](../journal/)へ分ける。

## 配置

`{track}/{topic-kebab-case}-results.md`を基本とし、対応するIssueとテスト設計へリンクする。

- Androidの例: [Todo機能の回帰テスト実施記録](android/todo-regression-results.md)。
- 複数回実施する場合は日付・対象コミット・条件を区別し、過去の結果を上書きして今回の合格にしない。

## 記載する内容

- 実施日、対象ブランチ・コミット、端末／EmulatorとOS、Backendなどの実行条件。
- 対象データの識別子と準備方法、必要な一時変更と復旧結果。
- ケースID、実際の操作、実際の結果、判定、関連する証拠・不具合Issue。
- 未実施・実施不可の項目と理由、既知の制約。

判定は未実施・合格・不合格・実施不可などで区別する。既知の制約を観察した結果は、その制約を解消できたという合格と混同しない。複数条件がある場合は個別の実施範囲を追えるようにする。

開発者の操作報告とエージェントの静的確認を区別する。画面共有やDB画像が示す範囲を明確にし、保管していない画像・録画・ログをリポジトリ内に存在する証拠として扱わない。未記録の条件や未実施の検証を補完して合格にしない。

終了時には確認用コードの除去と通常構成での最終確認を記録する。Git・GitHubへの書き込みは開発者が行う。
