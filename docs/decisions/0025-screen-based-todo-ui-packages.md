# 0025 - Todo UIは画面別パッケージにまとめる

**ステータス**: 採用
**日付**: 2026-10-18

## Context（背景・何を解決したいか）

ui/todoには4画面のRoute、Screen、UiState、ViewModel、Factoryが計20ファイル集まっていた。登録や編集など1画面の機能を変更する際、複数種類のファイルを一緒に読み、変更することが多い。関連ファイルを近くに配置し、探索と変更範囲の把握を容易にしたい。

## Decision（何を決めたか）

ui/todoの下をlist / detail / create / editに分け、各画面の5ファイルをまとめる。削除は詳細画面の操作なのでdetailへ含める。既存のクラス・関数名と責務は維持する。

Navigationは複数画面をつなぐためui/navigationへ、テーマはui/themeへ残す。共通ScaffoldとSnackbarはMainActivityに置く。共有する具体的な部品が必要になるまではcommonやutilを追加しない。

この配置をTodo UIの画面追加・変更の基本方針とする。配置を変えるだけで依存制約が強制されるわけではなく、画面同士で別画面のViewModelを直接呼ぶ設計にはしない。モジュール分割や新しいレイヤーの追加は別の問題として判断する。

## Consequences（この決定によって何が得られ、何を犠牲にしたか）

1画面の状態・操作・描画を同じ場所で追える。画面を追加する場合も、関連ファイルの配置先が明確になる。

一方、すべてのViewModelやScreenを横断して比較する場合は、複数の画面パッケージを開く必要がある。画面内のファイル数が増えた場合や実際の共有要件が生じた場合には、その問題に応じて再検討する。

### 代替案

- 平置きの継続: 階層は浅いが、4画面分が混在する状況を改善しない。
- route / screen / viewmodel / state / factory別: 同じ種類の実装を比較しやすく、技術的な役割が構成に表れる。一方、1画面の機能変更で複数の場所を行き来する。今回は画面単位の変更を優先して画面別を採用する。
- 画面ごとのGradleモジュール: 依存関係を制約できるが、今回の探索性の問題にはパッケージの整理で対応できるため導入しない。
