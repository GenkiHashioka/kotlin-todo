# 0012 - 統合テストで Testcontainers（実 PostgreSQL コンテナ）を使う

**ステータス**: 採用
**日付**: 2026-08-09

## Context（背景・何を解決したいか）

Phase 4.6 (b) で production ランタイムは PostgreSQL に切り替わったが、テストは依然として H2 in-memory に対して走っていた。`@DataJpaTest`（Repository slice test）はデフォルトで DataSource を embedded 版（classpath にある H2）に置き換える挙動があるため、H2 依存を残している限り自動的に H2 で走っていた。

この構成には次の問題がある：

- **DB 方言差の bug が検出できない**: PostgreSQL 特有の SQL 挙動（`GENERATED BY DEFAULT AS IDENTITY`、`ON DELETE CASCADE/SET NULL` の細かい挙動、`TEXT` 型の扱い、大文字小文字の識別子解決、etc.）を H2 では正確に再現できない。テストが green でも production で落ちる、という事故が起きやすい
- **Flyway migration が本番と違う DB に対して検証される**: `V1__init.sql` は PostgreSQL 用の DDL だが、H2 での互換性を保証しても意味が薄い（互換性が崩れた瞬間に production で気付く）
- **`docs/db-schema.md` と Entity と `V1__init.sql` の三者が本当に整合しているかを、実 DB を通しての検証で確認できない**

Phase 4.6 (a) の ADR 0010 で「Testcontainers 化まで Phase 4.6 のスコープに含める」と決めた。それを実装するのが本 PR (c)。

## Decision（何を決めたか）

**統合テストは Testcontainers 経由の実 PostgreSQL コンテナに対して走らせる**。具体的には：

- `build.gradle` の testImplementation に以下を追加：
  - `platform('org.testcontainers:testcontainers-bom:1.20.4')` — Testcontainers サブモジュール群のバージョン管理
  - `org.springframework.boot:spring-boot-testcontainers` — Spring Boot 4.x の Testcontainers 統合モジュール
  - `org.testcontainers:junit-jupiter` — JUnit 5 との統合、`@Testcontainers` / `@Container` の runtime
  - `org.testcontainers:postgresql` — `PostgreSQLContainer` クラスの提供
- **H2 依存 (`com.h2database:h2`) を削除** — テスト DB としても本番同一の PostgreSQL に統一
- 共通の基底クラス `AbstractPostgresTest` を導入し、`companion object` の `@Container @ServiceConnection` フィールドで PostgreSQL コンテナを 1 個だけ立てて JVM 内全テストで共有（Kotlin の companion object は class loader によって一度だけ初期化される特性を活用、コンテナ起動コスト ~5s を amortize）
- `@ServiceConnection`（Spring Boot 3.1+ の機能）で Spring の DataSource プロパティを Testcontainer の接続情報で自動配線 — 旧来の `@DynamicPropertySource` 手動注入の boilerplate を回避
- `TodoRepositoryTest` は `@DataJpaTest` を維持しつつ `@AutoConfigureTestDatabase(replace = Replace.NONE)` を追加、slice test でも application.properties の DataSource（= @ServiceConnection で書き換わる Testcontainer 接続）を使わせる
- Kotlin の `@Transactional` classes が final だと Spring proxy を作れないため、`TodoRepositoryTest` は `open class` として宣言

`PostgreSQLContainer(DockerImageName.parse("postgres:17"))` で docker-compose と同じイメージを指定 — 開発・本番・テストの DB バージョンを完全一致させる。

## Consequences（この決定によって何が得られ、何を犠牲にしたか）

### 得られるもの

- **本番と同じ DB でテスト**: SQL 方言差やスキーマ挙動が事前検証できる。Ktor + Exposed への移行後も同じ Testcontainer 資産をそのまま使い回せる（DB は変わらないため）
- **Flyway migration の実効性がテストで担保される**: 各テスト実行時に Flyway が Testcontainer 上で migrate を走らせるため、`V1__init.sql` が壊れた瞬間にテストが落ちる
- **テストと本番の一貫性**: 「テストは通るが本番で落ちる」の古典的問題が構造的に消える
- **CI 環境での再現性**: 開発機と CI で同じ image (`postgres:17`) を pull するため、環境差による flaky test が減る

### 犠牲にするもの

- **Docker daemon が必須**: 開発機・CI 両方で Docker が動いていないとテストが実行できない。従来の H2 in-memory ならデスクトップの Java 環境だけで完結していた
- **初回テスト実行が遅い**: PostgreSQL image の pull（初回のみ、~100MB）+ コンテナ起動（~5s）でオーバーヘッドが出る。2 回目以降は image がキャッシュされるので起動時間だけ
- **テスト全体の実行時間が増加**: 従来の H2 embedded と比べて、コンテナ起動と Flyway migration の分だけ遅い
- **CI で Docker-in-Docker（or 相当）の権限が必要**: GitHub Actions / GitLab CI 等で Docker socket にアクセスできる runner が必要（多くのマネージド CI では標準サポート）

### Spring Boot 4.x で踏んだ落とし穴（記録として）

本 PR 実装中に 3 つの環境要因で詰まった。将来の同種セットアップ時のために記録：

1. **`spring-boot-testcontainers` module を明示的に依存に足す必要がある**: Spring Boot 3.x では Testcontainers 統合が `spring-boot-autoconfigure` に同梱されていたが、4.x の modularization で独立モジュールに分離された。ADR 0011 の `spring-boot-flyway` と同じパターン
2. **Testcontainers BOM を明示的に `platform()` として足す必要がある**: Spring Boot 3.x の BOM は `org.testcontainers:*` のバージョンも管理していたが、4.x BOM は管理範囲を縮小し、Testcontainers サブモジュール (`junit-jupiter`, `postgresql`, etc.) のバージョンを解決できない。`platform('org.testcontainers:testcontainers-bom:1.20.4')` の明示が必要
3. **Kotlin の `@Transactional` テストクラスは `open class` として宣言する必要がある**: `@DataJpaTest` は暗黙に `@Transactional` を付与する。Spring は `@Transactional` の実装として proxy（サブクラス）を生成するため、対象クラスがサブクラス化可能である必要がある。Kotlin はデフォルト final なので、`kotlin.plugin.spring` プラグインが自動 open 化してくれるはず（の仕様）だが、`AbstractPostgresTest` を継承する構成にすると自動 open が効かない挙動を確認 — 明示的に `open class` を書くことで解決

### 代替案として検討したもの

- **H2 で押し通す**: 学習速度は上がるが、DB 方言差の事故を将来必ず踏む。学習プロジェクトとはいえ「production でも通用する構成」を身につけたい方針（[ADR 0010](0010-db-migration-before-framework-swap.md)）と矛盾するため却下
- **`@DynamicPropertySource` で Testcontainer 接続情報を手動注入**: `@ServiceConnection` 登場以前の古典的方式。書く量が多く、Testcontainer 以外の環境（開発、production）との切り替えロジックが煩雑になる。`@ServiceConnection` の方が「意図の宣言性」が高いため採用
- **テストクラスごとに `@Testcontainers` + `@Container` を持たせる（基底クラスを作らない）**: コンテナが各クラスで start/stop されて遅い。全テスト共有の基底クラス方式（現在の採用案）の方が amortize が効く
- **Testcontainers reuse mode（`~/.testcontainers.properties` の `testcontainers.reuse.enable=true`）**: JVM プロセス跨ぎでコンテナを再利用でき開発時のフィードバックが最速だが、CI では効かない。オプトインな高速化として本人がローカルで設定するのはあり、リポジトリの標準構成としては採用しない
