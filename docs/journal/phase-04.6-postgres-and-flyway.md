## 学んだこと

### Flyway の基本

- Flyway は「schema 変更を SQL migration file の**連番**で表現する」ツール。命名は `V{version}__{description}.sql` で、アンダースコアが 2 個必要（1 個だと Flyway が認識しない）
- 起動時に Flyway が `flyway_schema_history` テーブルを自動作成し、どの migration をいつ適用したかを記録する。同じ version は 2 度実行しない仕組み
- Spring Boot autoconfig が有効なら、起動時に自動で `migrate()` が呼ばれる。`docker compose up -d postgres && ./gradlew bootRun` だけで migration が走るのは、DevX として非常に楽

### `ddl-auto=none` と Hibernate/Flyway の役割分担

- Hibernate の `ddl-auto` は歴代 4 種類（`create`, `create-drop`, `update`, `validate`, `none`）ある。Phase 4 までは H2 の embedded モードで暗黙に `create-drop` が働いており、起動のたびに schema が再生成 → データが毎回消えていた
- Flyway に schema 管理を委ねると、Hibernate は「DDL には一切触らない」宣言が必要になる。それが `ddl-auto=none`
- もし両方を有効にすると、Hibernate と Flyway が「誰が schema を作るか」で衝突する。Flyway に一元化した方が「schema 変更の履歴が残る」「意図が明示される」「production で安全に運用できる」の 3 拍子揃う

### PostgreSQL 特有の DDL

- 自動採番列は 2 種類ある。旧来の `BIGSERIAL`（PostgreSQL 独自の糖衣構文、裏で sequence を作る）と、SQL 標準の `GENERATED BY DEFAULT AS IDENTITY`（PostgreSQL 10+）。今回は SQL 標準に寄せて後者を採用
- `BY DEFAULT` は「INSERT で明示値を書いてもよい、書かなければ自動生成」で、JPA の `GenerationType.IDENTITY` と自然に噛み合う。`ALWAYS` は明示値の指定を禁止する厳格モードだが、JPA 経由で意図せず衝突することがある
- FK の `ON DELETE CASCADE` / `ON DELETE SET NULL` は、JPA Entity 側の `@OnDelete(action = ...)` と DB 側で**両方一致**していないと、片方から削除したとき整合性が崩れる。Kotlin/JPA では Hibernate 独自の `org.hibernate.annotations.OnDelete` を使う（`jakarta.persistence` にはない）

### Spring Boot 4.x の modularization gotcha

- **今回一番ハマった点**。Boot 3.x では `flyway-core` を classpath に置くだけで autoconfig が起動していたが、Boot 4.x では `FlywayAutoConfiguration` が `spring-boot-autoconfigure` から独立モジュール `spring-boot-flyway` に切り出された
- `flyway-core` と `flyway-database-postgresql` を足したのに Flyway が起動しない、`bootRun` が `relation "users" does not exist` で落ちる、という現象で 30 分ハマった
- 診断は `application.properties` に `debug=true` を追加して起動時の **CONDITIONS EVALUATION REPORT** を出力させ、`FlywayAutoConfiguration` が Positive matches にも Negative matches にも居ないことを確認 → autoconfig 候補にすら入っていない → 提供モジュールが変わったと結論
- `~/.gradle/caches/modules-2/files-2.1/org.springframework.boot/` の中を `ls` してみると `spring-boot-data-jpa`, `spring-boot-jdbc`, `spring-boot-hibernate`, `spring-boot-h2console`, `spring-boot-jackson`, ... と 30 以上の細切れモジュールが並んでいて、Boot 4.x の modularization 方針が一目で分かった
- 修正は `implementation 'org.springframework.boot:spring-boot-flyway'` を 1 行足すだけ。ただし「なぜこれが必要か」を理解していないと、次に別のライブラリで同じ現象を踏む
- **教訓**: Spring Boot が暗黙にやってくれることに依存すると、フレームワーク major version bump で挙動が変わったとき謎エラーになる。Boot 4.x の「必要な統合モジュールを明示する」思想の方が、依存の意味が build.gradle だけで読める分、保守性が高い

### autoconfig の debug 手法

- `debug=true` プロパティで **CONDITIONS EVALUATION REPORT** が起動時に出る。全 autoconfig の判定結果（Positive / Negative / Unconditional）が見えるので、「なぜ動くべきものが動かないか」を切り分けられる
- `logging.level.org.flywaydb=DEBUG` のようにパッケージ単位で DEBUG log を有効化できる。特定のライブラリが「そもそも動いてるのか動いてないのか」を確認する時の第一手
- `./gradlew dependencies --configuration runtimeClasspath | grep <library>` で classpath 上の依存を確認できる。「依存が入っているのに autoconfig が起動しない」という診断の一次情報

### Flyway の checksum と V1 の不変性

- Flyway は各 migration file の checksum を `flyway_schema_history` に保存し、起動時に「以前適用した V1 の checksum」と「今の V1 file の checksum」を比較する。ズレていると `FlywayValidateException: Migration checksum mismatch` で起動を拒否する安全装置がある
- 本番運用が始まったら**既存 V1 を絶対に書き換えず、差分は V2/V3/... で新規追加する**のがルール
- Phase 4.6 は本番運用前で開発 DB のみなので、V1 を書き換えたら `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` で全消し → 再起動で V1 を最初から流し直せる。今回インデックス 1 本が漏れていたので、この手で修正した
- Phase 5 以降でフィルタ / ソート / 検索の実装時に、新規インデックスが必要になれば V2 を書く機会が来るはず

### PostgreSQL の運用小ネタ

- `docker compose exec postgres psql -U kotlin_todo -d kotlin_todo` で PostgreSQL コンテナ内の psql に入れる。`\dt` でテーブル一覧、`\di` でインデックス一覧、`\d <table>` でカラム定義
- `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` は「schema 内のオブジェクトを全消しして schema を再作成」の常套句。DB 自体は残る
- 開発サイクルで「PostgreSQL 起動してから bootRun」の順序が固定化した。Phase 4 の H2 in-memory 時代の「bootRun 単体で完結」の気楽さは失われたが、実運用に近い構成に一歩近づいた

## 実運用に関わる既知の課題（今回は対応を見送り）

- **テストが H2 で動いたまま**: `@DataJpaTest` は依然 H2 in-memory に対して走る（`com.h2database:h2` を保険で残しているため）。テストと本番で DB が違うと「テスト green だが本番で SQL 方言差で落ちる」古典的問題が起きる。PR (c) で Testcontainers PostgreSQL に切り替えて解消する
- **DevDataInitializer の冪等性**: 現状は起動のたびに「固定ユーザーが居なければ INSERT」なので、schema 保持されたまま bootRun を再起動すると重複しない。ただしトランザクション周りの正確な挙動は Phase 4 の DevDataInitializer の実装依存で、PostgreSQL に切り替えたことで新たな挙動が出る可能性がある（今回の smoke test では問題なし）
- **接続情報が平文**: `application.properties` に `password=kotlin_todo` が平文で書かれている。Phase 6 の認証実装時、または production を意識する段階で環境変数化する必要がある
