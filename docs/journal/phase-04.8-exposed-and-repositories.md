## 学んだこと

### Exposed の Table 定義は「schema の宣言」

`V1__init.sql` が DDL 発行者、Exposed の Table 定義は **「その schema を Exposed から見える形にする」宣言** という役割分担を体感した。JPA + `ddl-auto=update` の時代は「Entity を書けば裏で DDL が発行される」暗黙モデルだったが、Exposed では両者は完全に分離されている。**同期は手動**なので、`V1__init.sql` を変更したら Table 定義も揃える必要がある（V2 で列追加時など）。

`.autoIncrement()` は「Exposed 側で INSERT 時に id 列を省略する」宣言。DB 側は既に `GENERATED BY DEFAULT AS IDENTITY` になっているので、DB が id を採番する。Exposed 側の宣言は「振る舞い」の指定であって「DDL の生成源」ではない。

`.references(Users.id, onDelete = CASCADE)` も同様。FK 制約自体は Flyway が既に作っている。Exposed 側の `.references` は「join 時の型情報 + Exposed が生成する SQL の外部キー整合性のヒント」として機能する。DB 側の実効挙動は V1__init.sql の `REFERENCES users(id) ON DELETE CASCADE` が担う。

### `data class` + `val` = Phase 4 時代にはできなかった immutable ドメイン

Phase 4 の JPA 時代、Entity は **`data class` にできなかった**（Hibernate のプロキシ・変更検知・遅延ロードが `equals`/`hashCode` 自動生成と噛み合わない）。Exposed DSL では Entity クラスの概念自体が消え、ドメインクラスは Exposed から完全に切り離されている。結果として：

- `data class User(val id: Long, val email: String, ...)` の形が使える
- 全フィールド `val`（immutable）で書ける
- `equals` / `hashCode` / `toString` / `copy` が自動生成
- Kotlin の関数型スタイルと相性が良い

「Java でよく `@EqualsAndHashCode` を Lombok で自動生成していた作業が、Kotlin では言語標準で入っている」感覚。

### `suspend fun` + `newSuspendedTransaction(Dispatchers.IO)` パターン

Repository の全メソッドが `suspend fun` になり、内側で `newSuspendedTransaction(Dispatchers.IO) { ... }` を呼ぶ。この 3 つが噛み合って以下が実現する：

- **トランザクション境界の明示化**: `{ }` の中で BEGIN、正常終了で COMMIT、例外で ROLLBACK。JPA の `@Transactional` はメソッドの外から AOP で刺さっていたが、Exposed では自分の目に見える形で書く
- **coroutine 対応**: 中で他の suspend 関数を呼んでも、トランザクションはこのブロック内で維持される
- **DB クエリを IO 専用スレッドに逃がす**: `Dispatchers.IO` を渡すことで、Netty のイベントループスレッドで DB 待ちにならない

Ktor + Exposed のイディオムとして、Repository はほぼ全部この形になる。「同じパターンを繰り返すことで、脳の負担が減る」タイプのフレームワーク設計。

### Exposed DSL の主要イディオム 4 つ

1. **`Users.insert { it[Users.email] = ... } get Users.id`**: INSERT + 生成 id 取得。`get` は Kotlin の中置演算子っぽい記法で、返り値の Long を取得
2. **`Users.selectAll().where { Users.id eq id }.singleOrNull()`**: SELECT。`.selectAll()` で列指定、`.where { }` で条件、`.singleOrNull()` で 1 行 or null。0.60 以降の推奨構文（旧 `.select { }` は非推奨）
3. **`Users.update({ Users.id eq id }) { it[Users.title] = newTitle }`**: UPDATE。第 1 引数のラムダで WHERE、第 2 引数で SET
4. **`Users.deleteWhere { Users.id eq id }`**: DELETE。返り値は削除された行数

`eq`, `neq`, `less`, `greater`, `like`, `inList` などが中置演算子として定義されていて、SQL に近い読み心地。

### `ResultRow` → ドメイン変換を拡張関数で

```kotlin
private fun ResultRow.toUser(): User = User(
    id = this[Users.id],
    email = this[Users.email],
    ...
)
```

Kotlin の **拡張関数** で `ResultRow` に `toUser()` メソッドを外部から追加。`private` なので Repository 外に漏れない。使う側は `.singleOrNull()?.toUser()` のように綺麗に繋がる。

Java だと `UserMapper.mapRow(rs)` みたいな static utility method を書くところ、Kotlin は自然な文法で書ける。**「Exposed の実装詳細 (ResultRow) を Repository の外に漏らさない」設計が言語機能でサポートされている**。

### Enum ↔ String 変換は明示的に

Table 側は `varchar("priority", 20)`、Kotlin 側は `Priority.HIGH` 型。境界での変換を明示的に書く：

- 保存: `it[Todos.priority] = priority.name` → `"HIGH"` 文字列に
- 取得: `Priority.valueOf(this[Todos.priority])` → `Priority.HIGH` に

ADR 0001（enum は STRING で保存）の実装。DB に想定外の文字列（`"XYZ"`）があれば `Priority.valueOf` が例外を投げるので、silent 失敗しない。

### Testcontainers を Spring integration 無しで使う方法

Phase 4.6 (c) は `spring-boot-testcontainers` + `@ServiceConnection` で「Spring が全部やってくれた」。Ktor では autoconfig が無いので **明示的に自分で組み立てる**：

```kotlin
companion object {
    private val postgres: PostgreSQLContainer<*> = PostgreSQLContainer(...)
        .apply { start() }  // 手動 start

    init {
        val dataSource = HikariDataSource(HikariConfig().apply {
            jdbcUrl = postgres.jdbcUrl
            username = postgres.username
            password = postgres.password
            ...
        })
        DatabaseFactory.init(dataSource)  // 手動 init
    }
}
```

**Kotlin の companion object は JVM のクラスロード時に 1 度だけ初期化される**ので、この構造で「Testcontainer を JVM 内で 1 個だけ起動、全テストで共有」が自然に実現される。`@Testcontainers` アノテーションを使わなくても同じ効果が得られる。

### JUnit 5 + Kotlin のテスト書き方

- **`runBlocking { }`**: `@Test` の非-suspend 関数から `suspend fun` を呼ぶ橋渡し。`fun test() = runBlocking { ... }` の単一式関数記法が定番
- **バッククォート命名 `` `テスト名を日本語で書く`() ``**: JUnit のレポートに日本語がそのまま出る。テストが「何を確認しているか」が一目で分かる
- **`@BeforeEach fun cleanUp()`**: 各テスト前に走るフック。Testcontainer が JVM 内で共有される設計なので、テスト間のデータ独立を保つために必須
- **`transaction { }`（非-suspend）** を `@BeforeEach` で使う: JUnit のフックは非-suspend なので、`newSuspendedTransaction` ではなく同期版を使う
- **削除順は子から親**: `Todos → Categories → Users`。FK 制約に反すると失敗する

### FK SET NULL は DB 側で発火（CASCADE は今回未検証）

「Category を削除すると Todo の categoryId が null になる」テストで、**Repository コードは `categoryRepository.delete(category.id)` を呼んだだけ**。Todo の categoryId は明示的に触っていないが、テストで null になっていることを検証できた。

これは **PostgreSQL の FK 制約 `ON DELETE SET NULL` が発火した結果**。ADR 0002 / 0004 で決めた「削除連鎖は DB に任せる」方針のうち、SET NULL 側の実装確認ができた。Repository コードが薄くなるだけでなく、**「アプリケーションを経由しない SQL 直操作でも、削除連鎖は動く」ことが保証される**利点もある。

**一方で `ON DELETE CASCADE`（User 削除 → 関連する Todo / Category が連鎖削除）は今回テストしていない**。ADR 0002 の判断内容としては V1__init.sql と Exposed Table 定義の両方に `onDelete = CASCADE` は書かれており仕組みとしては動くはずだが、実テストによる裏付けは Phase 4.11 の「テスト戦略再構築」で追加する。SET NULL と CASCADE では PostgreSQL 側の挙動が微妙に違う（SET NULL は該当行を UPDATE、CASCADE は該当行を DELETE）ため、片方だけの検証で両方を保証したことにはならない。

## 実運用に関わる既知の課題（今回は対応を見送り）

- **Service 層がまだ無い**: Repository を直接テストしているが、実際の使い方（バリデーション、複数 Repository の組み合わせ、業務ルール）は Phase 4.9 で Service が入る
- **Ktor Routing との接続はまだ**: Repository はできたが、Ktor の `/todos` などのエンドポイントからは呼ばれていない。Phase 4.9 で `Application.module()` の routing ブロックで Service 経由の Repository 呼び出しを組む
- **依存注入は暫定的**: 現状の Repository は `class UserRepository()` の bare class、テストで new して直接使っている。手動 DI（ADR 0014）の本格運用は Phase 4.9 で `Application.module()` の依存グラフ組み立てとして実装
- **接続情報のハードコード継続**: DatabaseFactory の production 用 `init()` はまだハードコード（Phase 4.6 (a) の課題を継承）。Phase 6 の認証以降で外部化予定
- **`Thread.sleep(100)` に依存するテスト**: updatedAt テストは 100 ms の sleep で時刻差を確保。CI 環境などで flaky になる可能性あり。`Clock` 注入や `Awaitility` に切り替えるのが根本改善だが、今回は保留
- **`org.jetbrains.exposed.sql.transactions.experimental` 名前空間**: `newSuspendedTransaction` はまだ `experimental` パッケージにあり、将来 API 変更の可能性あり。Exposed のバージョンアップ時に確認する
- **`ON DELETE CASCADE` の実挙動未検証**: V1__init.sql と Exposed Table 定義の両方で User 削除時の Todo / Category 連鎖削除を宣言しているが、実テストは書いていない。ADR 0002 の判断が実装通り動くかを確認するテスト（例：User を削除すると、その User が owner の Category と Todo が全部消える）を Phase 4.11 で追加予定
