# Android 10 - Todo UIを画面別パッケージへ整理する

**記録日**: 2026-10-18
**対応Issue**: [#58](https://github.com/GenkiHashioka/kotlin-todo/issues/58)
**ブランチ**: refactor/android-todo-ui-packages
**設計メモ**: [Android 10](../../design-notes/android/10-todo-ui-packages.md)（実装前にレビュー）

## 実装結果

ui/todo直下の20ファイルをlist / detail / create / editへ各5ファイルずつ移動した。各画面のRoute、Screen、UiState、ViewModel、Factoryを同じ場所にまとめ、package宣言を更新した。MainActivityのFactory関数4つとNavHostのRoute・ViewModel計8つのimportも更新した。

開発者がAndroid Studioの移動機能を使い、一覧、詳細、登録、編集の順で1画面ずつ移動した。各段階でCodexが差分を確認し、開発者が動作確認を行った。削除処理は詳細に含まれる。Navigation、テーマ、共通Snackbar、Repository、通信モデルの配置は維持した。

## 学びと設計理由

### 種類別と画面別の比較

route / screen / viewmodel / state / factory別の構成は、技術的な役割が見えやすく、同種の実装を比較しやすい。一方、入力項目の追加など1画面の変更では複数の場所を行き来する。

今回は登録・編集など画面単位の変更が多いため、その作業単位に配置を合わせた。画面別にも種類別にも利点があり、一般的かどうかだけで選ぶのではなく、どのファイルを一緒に読むかを判断基準にした。大枠のui / dataという役割別の分割と、ui/todo内の画面別の分割は両立する。

### 配置と責務の違い

パッケージはコードの配置と名前の整理であり、それだけで処理の責務や依存関係が変わるわけではない。Routeは状態監視とcallback接続、Screenは描画と操作制御、ViewModelは状態管理とRepository呼び出し、Factoryは依存の受け渡しを継続する。

同じ画面の5ファイルをまとめて移したため、画面内の型同士は移動後も同じパッケージにある。外側のMainActivityとNavHostはimportの更新が必要だった。IDEの自動修正を使った後も、実際のpackage・import・内容を確認した。

## 設計との差分とADR

配置と作業手順は設計どおりであり、処理の共通化・改名・新しいレイヤー追加は行っていない。今後のTodo UIの配置にも適用する方針と、種類別を選ばなかった理由を[ADR 0025](../../decisions/0025-screen-based-todo-ui-packages.md)へ記録した。モノレポ構成と成功後の再取得通知の既存方針は維持する。過去のdesign-noteやjournalの旧パスは当時の記録として変更しない。

## 検証

### 開発者の手動確認報告

各画面の移動後、提示した確認項目について問題ない旨の報告があった。

- 一覧: ビルド、一覧表示、詳細への遷移。
- 詳細: 詳細表示、編集への遷移、削除キャンセル、削除成功後の一覧更新とSnackbar。
- 登録: ビルド、登録画面への遷移、登録成功後の一覧更新とSnackbar。
- 編集: ビルド、編集画面への遷移、既存値の表示、保存後の詳細更新とSnackbar、一覧へ戻った際の更新反映。

### Codexの静的確認

全20ファイルについてHEADの移動前の内容と比較し、package宣言以外の変更がないことを確認した。MainActivityとNavHostもimportの更新のみであり、参照先は移動先と一致する。各サブパッケージは5ファイル、ui/todo直下にKotlinファイルはなく、Androidソースに旧位置へのimportは残っていない。

ステージ済み・未ステージ両方のgit diff --checkを実行した。文書更新後には関連文書のローカルリンクも確認した。CodexはAndroidのビルド・エミュレータ操作を行っていない。自動テストは追加していない。

## 制約と次の課題

今回は配置変更に対する主要経路を確認した。通信失敗・タイムアウト・処理中の操作制御などを網羅した機能横断の回帰テストを実施したという意味ではない。

CRUDと補助機能、配置整理が揃ったため、次は回帰テストの対象・手順・期待結果を整理し、自動化する範囲を検討する。結果不明時の整合回復、レイアウトやタップ範囲、一覧の並び順などは引き続き後続課題とする。
