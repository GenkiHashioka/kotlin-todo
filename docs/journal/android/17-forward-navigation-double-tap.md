# Android 17 - 画面を進む操作の連打で同じ画面が2重に開かないようにする

**記録日**: 2026-11-21  
**対応Issue**: [#78](https://github.com/GenkiHashioka/kotlin-todo/issues/78)  
**ブランチ**: `fix/android-forward-navigation-double-tap`  
**設計メモ**: [Android 17](../../design-notes/android/17-forward-navigation-double-tap.md)（実装前にレビュー）

本書では、Composeの部品や関数を「日本語の名前（`コード上の名前`）」の形で書く。コード上の名前は、各節の初出に添える。

## 実装結果

設計メモの実装ステップどおり、「Todoを作成」→ 一覧の行 → 詳細の「編集」の順に実装・レビュー・動作確認した。変更したのは画面遷移の定義（`KotlinTodoNavHost`）だけである。

| 操作 | 実装 |
|---|---|
| 一覧の「Todoを作成」（`onCreateClick`） | 画面が操作を受け付けている状態（`RESUMED`）のときだけ処理を通す仕組み（`dropUnlessResumed`）で包んだ。#74 の戻る操作（`onBack`）と同じ形 |
| 一覧の行の選択（`onTodoClick`） | どの Todo かを表す引数（`todoId`）を受け取るため、`dropUnlessResumed` では包めない。一覧画面の `backStackEntry`（画面の積み重ねの1枚分の情報）のライフサイクルが `RESUMED` 以上のときだけ、画面を移る処理（`navigate()`）を呼ぶようにした |
| 詳細の「編集」（`onEditClick`） | 一覧の行と同じ形。判定には詳細画面の `backStackEntry` を使う |

追加した import は、ライフサイクルの状態を表す `androidx.lifecycle.Lifecycle` の1つだけで、ライブラリは足していない。画面・ViewModel・UI State は変えていない。

## 学びと設計理由

### `navigate()` は呼ばれた回数だけ画面を積む

`navigate()` は、呼ばれるたびに画面の履歴（バックスタック）へ画面を1つ積む。1回目のタップで画面の切り替えアニメーションが始まっても、終わるまでは前の画面が表示されたまま押せる。そのため2回目のタップでもう一度呼ばれ、同じ画面がもう1つ積まれる。#74 の `popBackStack()`（呼ばれた回数だけ戻る）と、向きが逆なだけで同じ原因だった。

直す前に、Pixel 8 のエミュレーターでマウスの連打を試した。

| 操作 | 連打した結果（対策前） |
|---|---|
| 一覧の行 | 再現した。詳細画面が2つ開く |
| 詳細の「編集」 | 再現した。編集画面が2つ開く |
| 一覧の「Todoを作成」 | 再現しなかった |

「Todoを作成」が再現しなかったのは、マウスの2回目のタップが遷移の終わりに間に合わなかったためと考えている（要確認）。`navigate()` を呼ぶしくみは3つとも同じで、実機の指で速く押せば起きる可能性があるため、予定どおり対処した。

### `dropUnlessResumed` の中身は「`RESUMED` 以上なら通す」という判定

`dropUnlessResumed` は引数のない処理（`() -> Unit`）しか包めない。一覧の行と「編集」は `todoId` を受け取る処理（`(Long) -> Unit`）なので、同じ判定を自分で書いた。

```kotlin
onTodoClick = { todoId ->
    if (backStackEntry.lifecycle.currentState.isAtLeast(Lifecycle.State.RESUMED)) {
        navController.navigate(TodoDetailDestination(todoId = todoId))
    }
},
```

`dropUnlessResumed` は、そのとき組み立てている画面のライフサイクル（`LocalLifecycleOwner`）を見る。`NavHost` の `composable<...> { }` の中では、それがその画面の `backStackEntry` になる。つまり上の判定は `dropUnlessResumed` と同じことをしている。引数がない「Todoを作成」は `dropUnlessResumed` で包み、引数がある2か所だけ判定を書いた。

| 案 | 判断 |
|---|---|
| 引数がない操作は `dropUnlessResumed`、引数がある操作は `backStackEntry` で同じ判定を書く | 採用。どちらも「その画面が `RESUMED` のときだけ通す」という同じ判定になる |
| 同じ画面が一番上にあれば積まない指定（`launchSingleTop = true`）を付ける | 不採用。違う行を素早く続けて選ぶと、別の Todo の詳細として2つ開く可能性がある |
| 画面側で、行ごとに `dropUnlessResumed` で包む | 不採用。連打対策が画面側へ散らばり、「画面遷移を扱う場所で止める」という #74 の考え方から外れる |
| 引数付きの処理を包む関数を自分で作る | 不採用。使うのは2か所だけで、関数を作るほどの重複ではない |

### 判定に使うのは、その画面の `backStackEntry`

判定には、`composable<...> { backStackEntry -> ... }` が受け取る、その画面の `backStackEntry` を使う。`navController.currentBackStackEntry` は「今一番上にある画面」を指すため、1回目のタップで遷移が始まった後は、開こうとしている新しい画面を指してしまい、判定が正しく働かない。一覧・詳細の `composable` は再取得の通知を受け取るために `backStackEntry` を既に受け取っていたので、それを使えた。

### 速い操作は、アニメーションを遅くして確かめる

違う2つの行を続けて押すケースは、遷移が速くてマウスでは間に合わなかった。端末の設定で、アニメーターの再生時間を10倍にして確かめた。

```bash
adb shell settings put global animator_duration_scale 10   # 10倍に伸ばす
adb shell settings put global animator_duration_scale 1    # 確認後に元へ戻す
```

Compose の画面切り替えアニメーションもこの設定に従うため、遷移中の時間がはっきり見え、その間に2つ目の行を押せた。ほかの方法は次の理由で採らなかった。

- デバッガーで止める：止めている間は画面の処理とライフサイクルの移り変わりも止まり、「遷移の途中で押す」状況にならない
- ログを足して `navigate()` の回数を数える：確かめるためだけのコードを足して後で消す必要がある
- `adb shell input tap` で2回押す：コマンドを1回動かすだけで時間がかかり、遷移中に2回目が届く保証がない

## 設計との差分と採否

設計メモとの差分はない。設計メモ 6章の懸念は次のとおり確かめた。

- 進んだ先から戻った後、もう一度押しても進める（戻った画面が再び `RESUMED` になる）。3つの操作とも本人がエミュレーターで確認した
- 画面を開いた直後のタップが捨てられる可能性：意図して試しておらず、未確認。#74 の Codex のレビューでは、捨てられても `RESUMED` に戻った後はもう一度押せるため、ずっと押せなくなる経路はないとされている
- 連打の速さ：「Todoを作成」はマウスでは再現できなかった（上の表）

## 検証

### 手動確認

Pixel 8 のエミュレーターで、本人が各ステップの実装後に確認した。

| 確認したこと | 結果 |
|---|---|
| 一覧の行、「Todoを作成」、詳細の「編集」を素早く連打する | 画面が1つだけ開き、1回戻ると前の画面に戻る |
| 違う2つの行を、遷移中に続けて押す（アニメーターの再生時間を10倍にして確認） | 詳細が1つだけ開く |
| 3つの操作を1回押す。戻ってからもう一度押す | 今までどおり進める |
| 詳細・登録・編集の戻るボタンの連打（#74 の回帰） | 1つ前の画面で止まる |
| 「登録」「保存」の連打 | 1回だけ登録・保存され、Snackbar も1つだけ出る |
| 削除の確認ダイアログの「削除」の連打 | 1回だけ削除される |
| 登録・編集・削除の成功後 | 自動で戻り、Snackbar が出て、一覧（編集では詳細も）が再取得される |

「登録」「保存」「削除」の連打は、ViewModel の送信中・完了済みの判定で止まると、着手前に Claude がコードを読んで予想していた（設計メモ 3.3）。今回の手動確認で、予想どおりであることを確かめた。

「再試行」ボタンの連打は、ViewModel に読み込み中かどうかの判定がなく、2回取得する可能性がある（設計メモ 3.3、Claude がコードから予想）。取得するだけで Todo は変わらないため、今回は直さず、確かめてもいない。

画面の小さいエミュレーター、横向き、実機では確認していない。

### 自動テスト

Windows 側で `testDebugUnitTest` を実行した。2026-11-21 21:56 の結果 XML で、タイトル整形のテスト（`TodoTitleTest`）4件と一覧 ViewModel のテスト（`TodoListViewModelTest`）6件の計10件が成功した（失敗・エラー・スキップ0件）。Claude が結果 XML を読んで確認した。今回は画面遷移の定義だけの変更のため、テストは追加していない。連打を確かめる UI テストは、画面遷移を含む UI テストの仕組みがまだないため書いていない。

### コードレビュー

各ステップの差分は Claude がレビューし、修正が必要な点はなかった。任意の提案として、一覧の行の判定に付けたコメントを「なぜ」を書く形にすることを挙げ、取り入れた（「編集」のコメントも同じ形で書いた）。

2026-11-21に、`main`との差分をCodexでレビューした（`/codex:review`）。修正が必要な不具合は見つからなかった。遷移元の`backStackEntry`のライフサイクルで判定している点と、連打防止を`KotlinTodoNavHost`に集める設計は適切で、既存の戻る操作・成功通知・再取得を損なう変更はないという結果だった。Codexはテストとエミュレーターでの確認は行っていない。

設計判断は #74 の考え方（画面遷移を扱う場所で、`RESUMED`のときだけ通す）を進む操作に当てはめたもので、新しい判断を含まないため、設計判断を疑うレビュー（`/codex:adversarial-review`）は実行していない。
