## 学びと設計理由

### 文字列を切り出さず、日時の型に直してから書式を当てる

```kotlin
private val todoDateTimeFormatter = DateTimeFormatter.ofPattern("yyyy/MM/dd HH:mm")

fun formatTodoDateTime(value: String): String? =
    try {
        LocalDateTime.parse(value).format(todoDateTimeFormatter)
    } catch (dateTimeParseException: DateTimeParseException) {
        null
    }
```

- 日時の型に直す処理（`LocalDateTime.parse()`）は、ISO 8601（国際標準の日時の書き方）の文字列を日時の型に直す
- 書式を当てる処理（`format()`）は、型紙（`DateTimeFormatter`）のとおりに並べて文字にする。型紙はファイルの中で 1 つだけ作って使い回す

着手前にバックエンドを読んで、API の日時の文字列は長さが決まっていないと分かった。バックエンドは `LocalDateTime` の `toString()` で文字列にしている。この書き方は秒が 0 なら秒を省き、小数の桁数も値によって 3 桁・6 桁・9 桁と変わる。文字列の先頭 16 文字を切り出す方法でも今の形なら動くが、日時として読まないので、壊れた値もそれらしい見た目で出てしまう。型に直す方法なら、読めない値は例外で分かる。

### 秒は「切り捨てる」のではなく「書かない」

`parse()` が作った日時の型には、秒とその下（`49.721526`）が残っている。秒が消えるのは `format()` の段階だが、計算して捨てているのではなく、型紙に秒の文字（`ss`）がないので文字にしないだけである。そのため `23:59:59.999999` も繰り上がらず `23:59` になる。これを 4 件目のテスト（`withLastSecondOfMinute_truncatesSeconds`）で確かめた。本人が説明した内容に、Claude がこの点を補った。

### 読めないときは `null` を返し、画面で「不明」と出す

設計メモの最初の下書き（v0.1）では、Claude は「読めないときは元の文字列をそのまま出す」案を推していた。本人のレビューで「確かめていない文字列を利用者に見せる道を残したくない」という指摘があり、実装前に方針を変えた。

| 案 | 判断 |
|---|---|
| 関数は `null` を返し、画面で「不明」と出す | 採用。戻り値が `String?` なので、呼ぶ側が `null` の扱い（`?:`）を書かないとコンパイルが通らず、扱い忘れを型で防げる |
| 空文字を返す（本人の最初の案） | 不採用。画面に「作成日時: 」とラベルだけが残り、表示が壊れたのか値がないのか区別がつかない |
| 「未設定」（既存の `unset`）を流用する | 不採用。作成日時・更新日時はサーバーが必ず入れる値で、意味が違う |
| 元の文字列をそのまま出す（Claude の最初の案） | 不採用。確かめていない文字列を利用者に見せる道が残る |

受け止める例外は `DateTimeParseException` だけにした。広く `Exception` を受け止めると、別の原因の不具合まで隠れる。

### テストを先に書き、「失敗できる」ことを確かめる

本人の希望で、7 件のテストをすべて書いてから本体を書いた。テストを先に書く場合、テストがコンパイルで止まると「確かめたいことが失敗した」状態にならない。そこで、まず `null` を返すだけの仮の関数を置いて、テストを動かせるようにした。

ただし、「`null` が返ること」を確かめる 6・7 件目は、`null` を返す仮の関数では最初から通ってしまう。そこで仮の関数を一時的に `"test"` を返す形に変えて、7 件すべてが失敗することを確かめた。これで、どのテストも間違った結果を見つけられることが分かった。

テストメソッド名は既存のテストと同じく `対象の関数_条件_期待する結果` の形にした。期待する値は、テストの中で `DateTimeFormatter` を使って作らず、`"2026/11/16 00:24"` と文字列で書いた。テストと本体が同じ間違いをすると、テストが通ってしまうためである。

### タイムゾーンは今回扱わない

API の日時はタイムゾーンを持たない。バックエンドは `LocalDateTime.now()`（サーバーの時計とタイムゾーン設定のままの日時）で記録している。サーバーと端末のタイムゾーンが違うと表示がずれるが、今はどちらも日本時間で実害がない。直すには API・DB・バックエンドのテスト・Android の受け取り方まで変わるため、別課題にした（下の「残る課題」）。

## 設計との差分と採否

実装は設計メモ（3.4 を本人のレビューで書き直した後の版）のとおりで、差分はない。

設計メモ 6章の詰まりポイントは次のとおりだった。

- import の取り違え、書式の大文字・小文字：起きなかった。`MM`（月）・`HH`（24 時間表記の時）の取り違えは、0 埋めのテスト（`withSingleDigitFields_padsWithZero`）でも確かめた
- 受け止める例外の範囲：`DateTimeParseException` だけにした
- 新しく作ったファイルの改行コードが CRLF（Windows の改行の形）になっていた。リポジトリの `.gitattributes` に `eol=lf` があるため、`git add` の時点で LF に直して記録される

### コードレビュー

テスト・本体・画面への組み込みは、各ステップで Claude がレビューした。動きに関わる指摘はなく、KDoc の追加と言葉（「時間」→「日時」）、コメント、`assertEquals(null, ...)` → `assertNull`、空行の指摘を取り入れた。

2026-11-22 に、コミット前の作業ツリーを Codex でレビューした。どちらもブランチを `main` との差分として指定したが、まだコミットしていなかったためブランチの差分は空で、Codex は未コミットの変更を読んでレビューした。Codex はテストを再実行していない。

| レビュー | 結果 |
|---|---|
| 通常のレビュー（`/codex:review`） | 修正が必要な不具合はなし。日時の変換は今の API の形式と合っていて、変換に失敗したときの「不明」の表示も適切とされた |

## 残る課題と次の作業

- API の日時にタイムゾーンを付ける：今は API がタイムゾーンを持たない日時を返し、バックエンドはサーバーの設定のまま記録している。着手条件は「サーバーを日本以外のタイムゾーンで動かすとき」か「次のプロダクトの要件で、日時を API に載せるとわかったとき」
- 編集の確認で、3 件目の Todo に Android 16 のサンプルデータにない説明「作成する。」が入った。次の撮り直しで Android 16 と同じデータを使えるよう、本人が説明を空に戻すことにした。一覧のスクリーンショットに説明は写らないため、README の画像への影響はない
