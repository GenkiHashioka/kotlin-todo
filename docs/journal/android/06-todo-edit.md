# Android 06 - Todoを編集し、詳細・一覧へ反映する

**記録日**: 2026-10-12
**対応Issue**: [#52](https://github.com/GenkiHashioka/kotlin-todo/issues/52)
**ブランチ**: `feat/android-todo-edit`
**設計メモ**: [Android 06: Todo編集](../../design-notes/android/06-todo-edit.md)

## 目的と実装結果

Androidから既存Todoの内容と進捗を更新する。詳細からIDを渡して編集画面へ進み、現在値をGETで取得してフォームへ設定し、PUTで保存する。成功後は詳細へ戻り、詳細と一覧を再取得する。

- TodoUpdateRequest、RetrofitのPUT契約、RepositoryのupdateTodoを追加した。
- 編集用Destination、Factory、ViewModel、UiState、Route、Screenを追加した。
- タイトル、説明、任意の期日、優先度、ステータスを編集する。
- ステータスは既存値を初期値にし、NOT_STARTED / IN_PROGRESS / DONEの選択順序を制限しない。
- カテゴリ選択は追加せず、取得したcategory?.idを保持する。
- 初期取得失敗は再試行、保存失敗は入力保持とエラー表示で扱う。
- 空白タイトル・送信中・更新済みの保存をガードし、送信中・更新済みの入力操作を無効にした。
- 成功時だけ詳細・一覧への再取得通知を保存し、編集画面を取り除く。

## 学びと設計理由

### 編集状態をDTOから分ける

通信のTodoDtoはレスポンスを表す。編集状態には変更中の入力値、送信中、保存失敗、更新済みなども必要になる。Editingへ必要な入力項目を分けて保持し、取得成功時に初期化する。再コンポーズのたびに初期値を入れ直さない。

Loading / LoadError / Editingをsealed interfaceで分け、取得前・取得失敗の状態に入力項目や保存操作を持たせない。保存失敗はEditingのフラグで表すため、入力を失わず再送信できる。

### PUTとカテゴリ保持

更新契約は[ADR 0005](../../decisions/0005-update-uses-put-not-patch.md)を継続する。カテゴリを編集しない場合もcategoryIdを保持する。nullを送るとカテゴリ解除になるため、選択UIがないことを理由に常にnullへ変換しない。

説明の空白はnull、期日はLocalDate?から日付文字列またはnullに変換する。登録時にステータスをNOT_STARTEDへ固定する処理は編集では使わない。

### StateFlowの更新と送信内容の確定

copyは新しい値を作り、_uiState.updateがその値を状態として保存する。入力更新・保存結果の更新は現在のEditingから必要な項目だけを変更する。updateのラムダは再評価され得るため、通信などの副作用を入れない。

送信内容は保存開始時のcurrentStateから確定する。結果反映時はupdateの引数から最新の状態を使う。通常のUIからメインスレッドで呼ぶ構成を前提に、launchより先にisSubmittingをtrueにして追加送信を拒否する。update単体で、状態の確認から通信開始までの一連の処理が原子的になるわけではない。

### 保存中の入力も制御する

全体レビュー時点では保存ボタンだけを無効にしており、送信中にもフォームを変更できた。例えば「A」を送信した後に画面を「B」へ変更すると、成功時には「A」が保存されて戻り、「B」が失われる。

送信中と更新済みには入力欄・優先度・ステータス・期日選択・解除も無効にした。保存失敗時はfinallyでisSubmittingがfalseに戻り、入力を保持したまま操作を再開できる。確認用に通信直前へ一時的なdelayを置き、スレッドを止めずに送信中の操作を確認した。記録時点のコードにdelayとそのimportは残っていない。

### 戻り先が詳細になると通知先も変わる

登録では直前の画面が一覧だが、編集では詳細になる。previousBackStackEntryで詳細へ通知し、getBackStackEntry(TodoListDestination)で一覧へ通知する。その後にpopBackStackする。現在の一覧・詳細・編集という経路を前提とする。

戻る操作や再コンポーズだけではAPIの新しい値は取得されない。各ViewModelが再取得し、StateFlowを更新した結果をComposeが表示する。通知のfalseへの変更は再取得要求の受付であり、通信完了ではない。再取得失敗は各画面のError表示とretryで扱う。

登録・編集で共通する判断として、[ADR 0023](../../decisions/0023-navigation-refresh-notification.md)へ通知と再取得の方針を切り出した。

## 設計との差分

IDから初期取得、カテゴリ保持、保存成功時の詳細・一覧更新は設計に沿って実装した。送信内容を開始時に確定する方針に対して、全体レビューで送信中の入力変更が失われる問題を見つけ、入力操作の無効化を追加した。実装前の意図を残すため、元の設計メモは書き換えていない。

## 検証

### 開発者からの確認報告

- 編集画面への遷移と既存値の表示。
- 保存成功後の詳細・一覧への反映。
- 保存ボタン押下後に入力操作ができなくなること。
- 保存失敗後に入力が残り、操作を再開できること。
- 説明と期日を解除して保存し、詳細画面で未設定として反映されること。
- 同じTodoを続けて2回編集し、どちらも詳細と一覧に最新値が反映されること。
- 入力を変更して保存せず戻っても詳細の値が変わらず、編集画面を再度開くと変更前の値が表示されること。
- ステータスを進行中・完了へ変更して保存し、それぞれ詳細と再度開いた編集画面に反映されること。
- 優先度を変更して保存し、再度開いた編集画面でも選択値が保持されること。
- ステータスを未着手へ戻して保存できること。
- タイトルが空または空白のみの場合、保存ボタンが無効になること。
- カテゴリが設定されたTodoを編集・保存しても、既存のカテゴリが保持されること。
- 編集画面の初期取得失敗でエラー表示になり、Backend復旧後の再試行で既存値がフォームに表示されること。画面遷移時にAPIから情報を取得すること。

## 後続課題

- `ui/todo`のファイル増加に対するパッケージ構成と責務・依存関係の見直し。削除機能まで揃った時点を候補とし、まず画面別の整理を検討する。探索や変更の把握が難しくなれば前倒しする。

- レイアウト、入力欄のラベル、ラジオボタンの文字を含む行全体の選択操作。
- 一覧の並び順。Backendの取得処理に明示的なORDER BYがなく、更新後の再取得で順序が変わり得る。ソート方針は別課題で決める。
- 送信中の表示、詳細な入力エラー、ViewModel / Repository / UIの自動テスト。
- プロセス再生成時の入力復元、競合更新やレスポンス喪失への対応。画面を戻ってもBackendの保存を取り消せる保証はない。
