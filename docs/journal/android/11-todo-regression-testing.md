## 実施結果

開発者がAndroid Emulator（Pixel 8 / Android 17.0）で、A01〜A17、B01〜B09、C01の計画ケースを順に確認した。同じケース内の複数条件は、実施記録に分けて記載した。Emulatorでの実施であり、実機・全端末・全OSでの確認を意味しない。

- 通常操作: 一覧・詳細、登録・編集・削除、任意項目の入力と解除、空白判定、ステータス変更、既存カテゴリの保持、保存せず戻る操作、削除確認のキャンセル、Empty、成功Snackbarと連続通知。
- 通信失敗と復旧: 一覧・詳細・編集の取得失敗と再試行、保存・削除失敗後の入力／詳細保持と操作復帰、復旧後の再送信。
- 処理中: Loading、保存・削除中の入力・追加送信・戻る操作の抑止と、失敗後の解除。
- 操作成功後の取得失敗: 登録・編集・削除は成功しても、戻り先の取得はErrorとなり得ること、再試行で保存・削除や成功通知を繰り返さないこと。
- 結果不明の観察: Backendでは削除済みでも、Androidは応答を受信できず失敗表示となり、古い詳細が残ること。

通常・異常系の計画した期待結果は開発者から確認報告を受けた。C01は整合回復の合格ではなく、既知の制約を観察した結果として区別した。最後に検証用コードをすべて除去し、Backend再起動とAndroidの通常構成で登録・編集・削除の一気通貫確認も行った。

今回は手動テストと記録の追加であり、Android・Backendの本番コードは変更していない。自動テストもまだ追加していない。

## 学び

### 操作と期待結果を先に定める

最初に「何を確かめるか」を説明し、準備・操作・判定の順で進めた。初期表示が正しいだけでなく、値を変えた後に操作可否が更新されることも確認した。例えばタイトルを入力後に消す操作は、初期状態の空文字とは到達経路が違う。

半角・全角スペースと改行だけの説明、そこへ空白以外の文字を1文字混ぜた説明も開発者が追加確認した。ifBlankの条件を満たす側と満たさない側の両方を見る観点につながった。

### 画面と保存データ、対象件数を区別する

UIの表示に加え、DBeaverで実データを照合した。DB画像が示すのは保存値であり、画面遷移やSnackbarは開発者の操作報告として記録した。会話で共有された画像自体はリポジトリへ保存していない。

REG62は回帰テストとIssue #62、後ろのA04などはケースIDを表す任意のデータ名とした。今回の対象が1件であることと、既存データを含むテーブル全体が何件かは区別した。テストデータのIDは明示指定せずDBの採番へ任せた。BY DEFAULT AS IDENTITYで手動指定できることと、採番器が自動調整されることは別であると確認した。

### 再現用の待機と本物の通信を区別する

処理が速い場面ではRepositoryのAPI呼び出し前に一時的なdelayを入れた。これはUIスレッドを止めず、処理中状態を観察する仕掛けであり、HTTPタイムアウトの検証ではない。

B09ではAPI操作の成功後に次の取得だけを例外にする一時フラグを使った。更新APIより前にフラグを立てた初稿は、更新自体が失敗しても取得失敗条件が残るため、成功後に立てるよう修正した。テスト用コードにも、狙う条件を正しく再現する必要がある。

### 事実・仮説・観察範囲を分ける

連続Snackbarで後の通知が短く感じられたという観察に対し、ダイアログ中にタイマーが止まるのではないかという仮説が挙がった。公開実装を確認し、開発者が録画で見直した結果、明確な差の再現は報告されなかった。厳密な秒数計測まで行ったとはしていない。

C01では削除後の応答を遅らせた。Backendの200ログが出ても、Androidが成功応答を受信した証拠にはならない。また35秒後にDBで削除済みだったことを、35秒後に初めて削除したと解釈しない。失敗表示だけではサーバーの実際の処理結果を断定できないことを確認した。

## 設計との差分とADR

文書レビューで実装設計とテスト設計を分ける方針に合意し、今回のテスト設計をdocs/design-notesからdocs/test-plansへ移した。実施結果はdocs/testing、学びは本journalへ記録する。既存の過去の設計メモは移動していない。

C01は実施前に設計を具体化し、削除前の遅延案から削除完了後の応答遅延へ変更した。クライアント切断によるキャンセルで削除自体が行われなくなる可能性と分け、削除済みなのにAndroidでは失敗になる条件を作るためである。タイムアウト後に新たに削除が完了する順序までは今回検証していない。

正常系のEmptyと最後の1件削除は、開発者の承認で既存のTodoを空にして確認した。過去に使ったIDがその後も存在する前提にはしていない。テストの進行に合わせ、未確認の枝分かれを別途補った。

既存のADR 0023の再取得通知、ADR 0024のタイムアウトを継続した。今回新しい本番構成やテスト基盤を導入していないため、新規ADRは追加しない。自動テスト構成の判断は後続Issueの設計時に扱う。

## 検証の責任と限界

端末操作・Backendの停止と再起動・DB確認・通常構成の一気通貫確認は、開発者からの報告に基づく。Codexは一時変更の差分、条件と処理順序、両cloneの検証用コード除去、git diff --check、文書リンクを静的確認した。CodexによるAndroidビルド・Emulator操作は行っていない。

実施記録は手順と報告を追跡する記録であり、すべての操作の録画やログを保管したものではない。Backendの基準コミット、最初と最後の一部のデータID、C01のクライアント例外種別と厳密な秒数など、未記録の情報も実施記録に明記した。

ViewModelを直接連続呼び出しする場合のガード、成功直後から自動遷移までの短い区間、Activity再作成、HTTPの全エラー種別は網羅していない。取得例外を注入したB09は実HTTP障害の検証ではない。

## 発見事項と後続の自動化

結果不明時の整合回復は未対応。削除済みの古い詳細が残ることと、失敗を断定するエラー文言は引き続き後続課題とする。一覧のタップ可能性が伝わりにくい点、タイトルの意図的改行の扱いも改善候補としてロードマップへ記録した。今回、機能修正を必要とする新規不具合として確定したものはない。

自動化の最初の対象は、一覧ViewModelのLoading / Success / Empty / Errorとretry / refreshを候補とする。対象が小さく、NavigationのIDや保存処理から切り離してCoroutineとStateFlowの検証を学べるためである。TodoApiのテスト用実装を既存TodoRepositoryへ渡す案とし、本番Repositoryへ検証用フラグを残さない。

保存・削除のガード、入力変換、Composeの操作無効、成功後の取得失敗の画面連携も後続候補だが、最初のIssueへ詰め込まない。一覧ViewModelの具体的な実装設計は後続Issueでレビューする。
