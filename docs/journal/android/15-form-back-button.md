# Android 15 - 登録・編集画面に画面上の戻るボタンを追加する

**記録日**: 2026-11-15  
**対応Issue**: [#74](https://github.com/GenkiHashioka/kotlin-todo/issues/74)  
**ブランチ**: `feature/android-form-back-button`  
**設計メモ**: [Android 15](../../design-notes/android/15-form-back-button.md)（実装前にレビュー）

本書では、Composeの部品や関数を「日本語の名前（`コード上の名前`）」の形で書く。コード上の名前は、各節の初出に添える。

## 実装結果

設計メモの実装ステップどおり、編集画面 → 登録画面の順に実装・レビュー・動作確認した。確認中に戻るボタンの連打で前の画面を越えて戻る不具合が見つかり、詳細画面を含む3画面の戻る処理に対処を加えた。

| 項目 | 実装 |
|---|---|
| 編集画面 | 戻る処理を受け取る引数（`onBack`）を足し、外側の縦並び（`Column`）の先頭に「戻る」ボタン（`Button`）を置いた。有効・無効（`enabled`）には、システムの戻る操作の横取り（`BackHandler`）と同じ `canGoBack` を使う |
| 登録画面 | 同じ引数とボタンを足した。画面全体が1つのスクロールする縦並びだったため、外側に縦並びを1段足し、今の縦並びを残りの高さを占める形（`weight(1f)`）で中に入れた |
| Route | `TodoCreateRoute` / `TodoEditRoute` に `onBack` を足し、加工せずに画面へ渡す |
| 画面遷移の定義 | `KotlinTodoNavHost` から、前の画面へ戻る処理（`navController.popBackStack()`）を渡す |
| 連打の対策（設計との差分） | 詳細・登録・編集の3画面の `onBack` を、画面が操作を受け付けている状態のときだけ処理を通す仕組み（`dropUnlessResumed`）で包んだ |

ViewModel と UI State は変えていない。成功後の自動遷移（`onCreated` / `onUpdated` / `onDeleted`）も変えていない。

## 学びと設計理由

### 戻る操作の条件を1か所で計算すると、2つの戻る操作がずれない

画面上のボタンとシステムの戻る操作は、どちらも同じ `canGoBack` から有効・無効を決める。条件を画面の中の1か所で計算しているため、片方だけ送信中に戻れてしまうことが起きない。#57 で作った条件を、そのまま使い回せた。

編集画面では、読み込み中・読み込み失敗のときは編集中の状態（`TodoEditUiState.Editing`）ではないため、`canGoBack` は `true` になる。ボタンを状態の切り替え（`when`）の外に置いたので、どの状態でもボタンが表示され、押せる。

### 画面は「戻りたい」と伝えるだけで、どこへ戻るかは知らない

画面は `onBack` を呼ぶだけで、画面遷移の仕組み（`NavController`）を知らない。どこへ戻るかは `KotlinTodoNavHost` が決める。詳細画面と同じ形にそろえたことで、後から連打の対策を入れるときも、`KotlinTodoNavHost` の3か所を変えるだけで済み、画面のコードには手を入れなかった。

### 組み替えるときは、受け取った `modifier` を一番外側の部品に渡す

登録画面では、外側に縦並びを足した。呼び出し元から受け取った `modifier`（画面全体の大きさ）は、新しい外側の縦並びに移し、内側は空の `Modifier` から書き始めた。受け取った `modifier` を受けるのは、画面の一番外側の部品1つだけにする。

内側の縦並びには `weight(1f)` を付け、ボタンを置いた残りの高さを全部使わせた。付けないと内容の高さしかなくなり、最後の項目より下の余白をタップしてもキーボードが閉じなくなる（#73）。外側のタップの検出（`pointerInput`）、キーボード分の余白（`imePadding`）、スクロール（`verticalScroll`）は、順番を変えずに内側に残した。

差分は字下げが1段深くなるため 147 行に見えたが、空白の違いを無視して比べる（`git diff -w`）と、実際の変更は 13 行だった。

### `weight` は縦並びの中身を書くブロックが持つ機能で、import は要らない

Claude は当初、「`weight` は import が必要」と説明した。実際は、縦並びの中身を書くブロック（`ColumnScope`）自体が持っている機能で、`Column { ... }` の中では import しなくても使える。差分に import が増えていないのは正しい状態だった。

### `popBackStack()` は呼ばれた回数だけ戻る

`popBackStack()` は、画面の履歴（バックスタック）から画面を1つ取り除く。1回目のタップで画面の切り替えアニメーションが始まっても、終わるまではボタンが表示されたまま押せる。そのため2回目のタップでもう一度呼ばれ、前の画面まで履歴から消える。

Pixel 8 のエミュレーターで、3画面とも再現した。

| 画面 | 連打した結果（対策前） |
|---|---|
| 詳細 | 2回で一覧も消え、画面が空になる |
| 登録 | 2回で一覧も消え、画面が空になる |
| 編集 | 2回で詳細も消えて一覧に戻る。3回で画面が空になる（履歴が一覧 → 詳細 → 編集と1段深いため） |

詳細画面の既存の戻るボタンにも同じ不具合があった。設計メモ 6章で可能性を挙げていたが、#74 より前には確かめていなかった。

### 連打は、画面遷移を扱う場所で止める

`dropUnlessResumed` は、画面が操作を受け付けている状態（`RESUMED`）のときだけ処理を通し、それ以外のときの呼び出しは捨てる処理を作る。`NavHost` の各画面は、遷移が始まった時点で `RESUMED` ではなくなるため、2回目以降のタップは捨てられる。使っている `lifecycle-runtime-compose` 2.11.0 に含まれており（2.8.0 で追加）、ライブラリは足していない。

| 案 | 判断 |
|---|---|
| `KotlinTodoNavHost` で `onBack` を `dropUnlessResumed` で包む | 採用。連打は画面遷移の問題なので、遷移を扱う場所で止める。変更は3か所とも1行 |
| 画面側で「押したか」のフラグを持つ（`remember { mutableStateOf(false) }`） | 不採用。3画面それぞれに同じ仕組みが要り、戻らなかった場合にフラグを戻す処理も考える必要がある |
| 今の画面の状態を自分で調べて判定する（`navController.currentBackStackEntry?.lifecycle?.currentState`） | 不採用。`dropUnlessResumed` と同じことを手書きするだけになる |

成功後の自動遷移（`onCreated` / `onUpdated` / `onDeleted`）は包んでいない。ボタンのタップではなく、成功したときに `LaunchedEffect` から1回だけ呼ばれるため、連打は起きない。

## 設計との差分と採否

| 差分 | 理由 |
|---|---|
| 3画面の `onBack` を `dropUnlessResumed` で包んだ | 設計メモ 6章で懸念として挙げ、問題が見つかった場合は検討するとしていた。エミュレーターで3画面とも再現したため入れた |
| 詳細画面の戻るボタンも変更した | 設計メモ 2章では「詳細画面の戻るボタンは変えない。連打の確認で問題が見つかった場合は扱いを相談する」としていた。原因と対処が同じで変更も1行のため、相談のうえ #74 に含めた。分けると、3画面のうち詳細画面だけが連打で壊れる状態が残る |

画面を進む操作の連打（一覧の行、「Todoを作成」ボタン、詳細の「編集」ボタン）でも同じ画面が2重に開くことが、確認中に見つかった。#74 の範囲（戻る操作）から外れるため、[#78](https://github.com/GenkiHashioka/kotlin-todo/issues/78) に分けた。

設計メモ 6章の懸念のうち、残りは次のとおり確かめた。

- 登録画面の組み替え後も、最後の項目より下の余白のタップでキーボードが閉じる
- キーボードを出したまま戻っても、戻った先の画面でキーボードが残らない。フォーカスを先に外す処理は足していない
- プレビュー（`@Preview`）で画面を呼んでいる箇所はなく、引数の追加漏れはなかった（Claude がコードを検索して確認）

## 検証

### 手動確認

Pixel 8 のエミュレーターで、各ステップの実装後と連打の対策の後に確認した。

| 画面 | 確認した内容 |
|---|---|
| 編集 | 戻るボタンで詳細へ戻れる。保存中はボタンが無効になる |
| 登録 | 最後の項目（登録ボタン）より下の余白のタップでキーボードが閉じる。キーボードを出したまま下までスクロールでき、戻るボタンは上に残ったまま見える |
| 登録・編集 | 入力途中で戻ると、もう一度開いたときに入力が残っていない。登録の送信中もボタンが無効になる |
| 登録・編集 | 成功すると自動で戻り、Snackbar が出て、一覧（編集では詳細も）が再取得される。失敗後はボタンが押せるようになり、戻れる |
| 編集 | 読み込み中・読み込み失敗のときもボタンが表示され、押すと詳細へ戻れる |
| 登録・編集 | キーボードを出したまま戻るボタンを押しても、戻った先の画面でキーボードが残らない |
| 詳細・登録・編集 | 対策前は、連打で前の画面を越えて戻った（上の表）。対策後は、2回・3回と素早く押しても1つ前の画面で止まる。1回押したとき、システムの戻る操作のときは今までどおり戻れる |

画面の小さいエミュレーターと横向きでは確認していない。

### 自動テスト

Windows 側で `testDebugUnitTest` を実行した。2026-11-15 17:00 の結果 XML で、タイトル整形のテスト（`TodoTitleTest`）4件と一覧 ViewModel のテスト（`TodoListViewModelTest`）6件の計10件が成功した（失敗・エラー・スキップ0件）。Claude が結果 XML を読んで確認した。今回は画面側と画面遷移の定義だけの変更のため、テストは追加していない。

### コードレビュー

各ステップの差分は Claude がレビューし、修正が必要な点はなかった。任意の提案として、編集画面のボタンと枠（`Box`）の間に、詳細画面と同じく空行を入れることを挙げ、取り入れた。

2026-11-15に、`main`との差分をCodexでレビューした（`/codex:review`）。修正が必要な不具合は見つからず、既存の`canGoBack`を使い回した操作制御と、NavHostでの連打防止は整合しているという結果だった。Codexはビルド・テスト・エミュレーターでの確認は行っていない。

連打の対策は設計メモの範囲外で決めた判断のため、設計判断を疑うレビュー（`/codex:adversarial-review`）も実行した。観点は「`dropUnlessResumed`で`NavHost`の戻る処理を包む判断に、取りこぼす連打や、戻るべき場面で戻れなくなるケースがないか」とした。判定は承認（approve）で、重大な指摘はなかった。

- 遷移中の古い画面からの追加の`popBackStack()`は止まる
- 画面に入るアニメーションの間の最初のタップも捨てられる。ただし、`RESUMED`に戻った後はもう一度押せるため、ずっと戻れなくなる経路はない
- 成功後の自動遷移は包んでいないため、影響しない

追加の確認として挙げられた「画面に入った直後のタップが捨てられた後、遷移が終わってからもう一度押すと戻れる」ことは、Pixel 8 のエミュレーターで確かめた。
