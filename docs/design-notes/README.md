# 詳細設計メモ (design-notes)

Phase / 機能を実装する **前に** 書く設計メモを配置するディレクトリ。案 C（現代的アーキテクチャ文書 + 実装前設計メモ）の「詳細設計相当」を担う。

## 目的

- **実装前に「これから何を作るか」を言語化** することで、いきなりコードを書き始めて設計が固まらないまま迷走する事態を防ぐ
- Claude と本人の間で **設計の合意点を明示的に記録** し、後から「なぜこう作ったか」を辿れる形にする
- **journal（実装後の学び）と対** になる。design-notes = 実装前の意図、journal = 実装後の結果と差分。両者を比較すると学びが深まる

## 使い分け（他のドキュメントとの棲み分け）

| ドキュメント | いつ書く | 何を書く |
|---|---|---|
| `requirements.md` | プロジェクト方針変更時 | プロダクトとして何を作るか（機能・スコープ） |
| `architecture.md` | アーキテクチャ変更時 | システム全体構成・レイヤー・依存 |
| `decisions/` (ADR) | 判断発生時 | 個別の設計判断（採用理由と代替案） |
| **`design-notes/`** (本ディレクトリ) | **Phase / 機能実装前** | **これから何をどう作るか、具体的な段取り** |
| `journal/` | Phase 実装後 | 何を作ったか、詰まった点、学び |

**design-notes は書き捨てで OK**。実装が終わったら基本更新しない。「あの時こう設計しようとした」記録として保存し、実際に何を作ったかは journal に書く。

## ファイル配置と命名規則

```
docs/design-notes/
├── README.md                                 # 本ドキュメント（運用ガイド）
├── phase-04.9b-ktor-routing-and-dto.md       # 例: Phase 4.9 (b) の設計メモ
├── phase-04.9c-konform-and-status-pages.md   # 例: Phase 4.9 (c) の設計メモ
└── phase-05-filter-sort-search.md            # 例: Phase 5 の設計メモ
```

**命名**: `phase-{Phase番号}-{topic-kebab-case}.md`

- Phase 番号は journal と揃える（例: `phase-04.9b-...`）
- topic は「何を作る PR か」を kebab-case で。design-notes は 1 Phase 内で複数書いても良い

## テンプレート

新規 design-note は以下 6 節構成。**「詰まりポイント」を書く** ことが特徴で、事前に懸念を言語化しておくと実装中に慌てない。

```markdown
# 詳細設計メモ - Phase XX-YY: {タイトル}

**バージョン**: 0.1
**最終更新**: YYYY-MM-DD
**対応 Phase**: Phase XX-YY

## 1. 背景

なぜこの Phase / 機能が必要か。要件書のどの項目に対応するか。前 Phase までの状態と、今 Phase で何が変わるか。

## 2. スコープ

### この PR で作るもの
- （箇条書き）

### この PR で作らないもの（次 Phase 以降 or 別 PR）
- （箇条書き）

## 3. 設計方針

主要な設計判断。複数選択肢がある場合は比較表 + 採用理由を書く。ここで固まった判断のうち、後で残しておく価値があるものは ADR に切り出す。

### 判断ポイント A
- 選択肢 A-1: ...
- 選択肢 A-2: ...
- 採用: A-1、理由: ...

## 4. 実装ステップ

大まかな作業順序。ファイル単位 or 機能単位で。

1. `xxx.kt` を新規作成、YYY を実装
2. `zzz.kt` を修正、AAA の呼び出しを追加
3. テスト N 件追加
4. `./gradlew test` で動作確認

## 5. 確認方法

どう動作確認するか。手動確認（curl コマンド、psql）とテスト（自動化）の両方を書く。

### 手動確認
- `docker compose up -d postgres && ./gradlew run`
- `curl -X POST http://localhost:8080/todos -d '...'`

### 自動テスト
- 追加テスト N 件が green

## 6. 想定される詰まりポイント

事前に気付いた懸念、対処案。実装中に「あ、これ想定してた」と思い出せる形で書く。

- 懸念 A: ...  → 対処案: ...
- 懸念 B: ...  → 対処案: ...
```

## 運用フロー

```
Phase X 着手前
    ↓
本人と Claude で設計相談（会話ベース）
    ↓
Claude が design-notes/phase-XX-{topic}.md を下書き
    ↓
本人がレビュー + 修正
    ↓
実装 PR に含めて commit（コードと同時 or 事前 PR で先行 merge）
    ↓
本人が実装（design-notes を参照しながら）
    ↓
実装完了後、journal を書く（design-notes との差分を意識）
    ↓
以降、design-notes は基本更新しない（意図の記録として保存）
```

## design-notes を PR に含める粒度

### パターン A（デフォルト、推奨）: 実装 PR と同梱

- **1 PR で完結**: `docs/design-notes/phase-XX-{topic}.md` の追加 + 実装 + テスト + journal 追記を同じ PR に含める
- **レビュー時に対比可能**: 設計と実装が同じ diff で並ぶので、齟齬があれば即座に気付ける
- **PR 数を抑えられる**: 学習プロジェクトのイテレーション速度を維持

**運用の注意**:
- **commit を分ける** ことで擬似的な時系列を残せる（例: `docs: add design-note for phase-XX` → `feat: implement phase-XX` の 2 コミット構成）
- 「本当に設計が先だったか」は git 履歴だけでは証明できず、本人の自己規律に依存する。意識的に「まず design-note を書いてから実装を始める」ルーティンを守ることが前提

### パターン B（例外時のみ）: 設計 PR を先行 merge、実装 PR は後続

- **PR-1**: `docs/design-notes/phase-XX-{topic}.md` を新規作成する docs-only PR、merge
- **PR-2**: 上記設計メモを参照しながら実装、テスト、journal 追記を行う実装 PR

**採用ケース**:
- 設計が複雑で、実装着手前に十分なレビューコメントをもらいたい場合
- 設計自体の議論が長引きそうで、実装まで含めると PR が重くなりすぎる場合
- 「設計 → 実装の時系列を git 履歴で明示的に固定したい」という要求がある場合

**本プロジェクトのデフォルト: パターン A**。パターン B は上記のような例外ケース時のみ採用。
