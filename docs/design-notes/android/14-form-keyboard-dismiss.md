# 詳細設計メモ - Android 14: 登録・編集画面でキーボードの外側をタップして閉じる

**バージョン**: 0.1
**作成日**: 2026-11-08
**対応Issue**: [#73](https://github.com/GenkiHashioka/kotlin-todo/issues/73)

## 1. 背景

#65 の動作確認で、登録・編集画面のキーボードは入力欄の外側をタップしても閉じないことが分かった。今閉じる方法は、システムの戻る操作しかない。#65 でスクロールとキーボード分の余白（`imePadding`）を直したため、キーボードが開いたままでも全項目と確定ボタンには届く。そのため #65 では対象から外し、この Issue に分けた。

着手前に Claude が登録・編集画面のコードを読み、タイトル欄の Enter キーの挙動は Pixel 8 のエミュレーターで確かめた。

| 対象 | 現状 | 根拠 |
|---|---|---|
| 外側のタップ | 背景のタップを拾う処理がない。入力欄がフォーカス（入力を受け付けている状態）を持ち続け、キーボードは開いたまま | コード（Claude） |
| ラジオボタン・期日・確定ボタン | それぞれの行やボタンがタップを処理するだけで、入力欄のフォーカスは外れない | コード（Claude） |
| タイトル欄の Enter キー | 1行入力（`singleLine = true`）だけで、キーボードの設定（`keyboardOptions`）は指定していない。押すとキーボードが閉じるが、フォーカスはタイトル欄に残りカーソルも表示されたまま | コード（Claude）、エミュレーター |
| 編集画面の入力欄の並び | 入力欄を並べる縦並び（`Column`）に大きさの指定がなく、内容の高さしかない。最後の項目より下の余白は、外側の枠（`Box`）の領域になる | コード（Claude） |

タイトル欄の Enter キーで閉じるのは、Compose の標準の動きによる。1行入力で Enter の位置の動作（`imeAction`）を指定しないと「完了（`ImeAction.Done`）」として扱われ、押したときの処理を書いていなければ、キーボードだけを隠す（`keyboardController.hide()`）。フォーカスは外れない。

関連文書: [Android 13: Todo画面の見やすさと操作性を改善する](13-todo-ui-usability.md)、[Android 13 の journal](../../journal/android/13-todo-ui-usability.md)、[ADR 0025: 画面別のTodo UIパッケージ](../../decisions/0025-screen-based-todo-ui-packages.md)。

## 2. スコープ

### この Issue で扱うもの

1. 登録・編集画面で、入力欄の外側の余白をタップするとキーボードが閉じる
2. ラジオボタンの行・期日のボタン・確定ボタンを押すと、その操作をしたうえでキーボードが閉じる
3. タイトル欄の Enter キーを「次へ」にし、説明欄へ移る

送信中の入力の無効化、送信中・送信済みの戻る操作の制御、キーボード表示中の到達性（#65）を維持する。

### 今回扱わないもの

画面全体のデザイン変更、入力欄の追加・変更（「閉じる」アイコンの追加を含む）、画面上の戻るボタン（TopAppBar、#74）、登録・編集画面の共通フォーム化。

## 3. 設計方針

### 3.1 外側のタップ：入力欄を並べる縦並びでタップを拾い、フォーカスを外す

入力欄を並べる縦並びに、タップを検出する処理（`pointerInput` と `detectTapGestures`）を付ける。タップされたら、フォーカスを管理する仕組み（`LocalFocusManager`）からフォーカスを外す（`clearFocus()`）。フォーカスが外れると、カーソルが消えてキーボードが閉じる。

```kotlin
val focusManager = LocalFocusManager.current

Column(
    modifier = modifier
        .pointerInput(Unit) {
            detectTapGestures(onTap = { focusManager.clearFocus() })
        }
        .imePadding()
        .verticalScroll(rememberScrollState())
        ...
)
```

- タップの検出は、子のボタンやラジオボタンの行がタップを処理済み（消費）にした場合は反応しない。余白をタップしたときだけ動く
- スクロールのためのドラッグはタップと判定されないため、スクロールを妨げない
- 登録画面の縦並びは、画面から全体の大きさ（`fillMaxSize`）を受け取っているため、項目の下の余白も含めて反応する
- 編集画面の縦並びは内容の高さしかないため、最大の大きさ（`Modifier.fillMaxSize()`）を付けて、外側の枠いっぱいに広げる。スクロールする内容は縦並びの中で動くので、見た目は変わらない
- 編集画面では、入力欄のある編集中の状態（`TodoEditUiState.Editing`）の縦並びにだけ付ける。読み込み中・読み込み失敗の状態には入力欄がないため付けない

| 案 | 判断 |
|---|---|
| タップの検出（`pointerInput` + `detectTapGestures`）でフォーカスを外す | 採用。余白のタップだけに反応し、子のボタンやスクロールを妨げない |
| 背景をボタン扱いにする（`Modifier.clickable`） | 不採用。押したときの波紋は消せるが、画面全体がボタンとして扱われ、TalkBack（画面読み上げ機能）が背景を押せる要素として読み上げる |
| キーボードだけ隠す（`keyboardController.hide()`） | 不採用。フォーカスとカーソルが入力欄に残り、入力中か終わったかが見た目で分からない |
| Activity でタッチを横取りする（`dispatchTouchEvent` の上書き） | 不採用。View 時代のやり方で、アプリの全画面に効き、対象の2画面に絞れない |

#65 で共通フォーム化を対象外にしたため、共通の部品にはまとめない。登録・編集の各画面に同じ数行を書く。

### 3.2 ボタン操作：各ボタンの処理でもフォーカスを外す

ラジオボタンの行、期日の「選択」「クリア」ボタン、確定ボタンを押したときも、フォーカスを外す。それぞれの押したときの処理（`onClick`）の先頭に `focusManager.clearFocus()` を足す。

```kotlin
RadioOptionRow(
    ...
    onClick = {
        focusManager.clearFocus()
        onPriorityChange(priority)
    },
)
```

| 画面 | 対象 |
|---|---|
| 登録 | 優先度の行、期日の「選択」「クリア」、確定ボタン（登録） |
| 編集 | 優先度の行、状態の行、期日の「選択」「クリア」、確定ボタン（保存） |

日付選択のダイアログ内のボタン（OK・キャンセル）には足さない。ダイアログを開く「選択」ボタンの時点でフォーカスを外しているためである。

| 案 | 判断 |
|---|---|
| 余白のタップ（3.1）＋各ボタンの処理でフォーカスを外す | 採用。「この操作をしたら入力は終わり」という意図が、各ボタンの処理を読めば分かる |
| 余白のタップだけ | 不採用。人が「外側」としてタップするのは、何もない余白より次に操作したいボタンのほうが多い。優先度を選んでもキーボードが開いたままで、下の項目が隠れたままになる |
| 親が子より先にタッチを受け取る指定（`PointerEventPass.Initial`）で、全部のタップをまとめて拾う | 不採用。入力欄の中をタップしたとき（カーソルを動かす、別の欄へ移る）にもフォーカスが外れ、キーボードが一瞬閉じて開く、カーソル位置がずれるおそれがある。入力欄だけ除く処理を足すと仕組みが分かりにくくなる |
| ボタンがフォーカスを受け取れるようにする | 不採用。タッチ操作では Compose のボタンは通常フォーカスを取らず、標準から外れた動きになる |

### 3.3 タイトル欄の Enter キー：「次へ」にして説明欄へ移る

タイトル欄のキーボードの設定（`KeyboardOptions`）で、Enter の位置の動作を「次へ（`ImeAction.Next`）」にする。押したときの処理（`keyboardActions`）を書かなくても、Compose の標準の動きで次の入力欄（説明欄）へフォーカスが移る。

```kotlin
OutlinedTextField(
    ...
    singleLine = true,
    keyboardOptions = KeyboardOptions(imeAction = ImeAction.Next),
)
```

説明欄は複数行の入力欄なので、Enter は今までどおり改行にする。説明の入力を終えたら、余白やボタンのタップでキーボードを閉じる。

| 案 | 判断 |
|---|---|
| 「次へ（`ImeAction.Next`）」 | 採用。上から順に入力する流れに合う。閉じる役は外側のタップ、Enter は次の欄へ進む役と分けられる |
| 「完了」のまま（現状。指定しない場合と同じ） | 不採用。コードを変えずに済むが、キーボードだけを隠しフォーカスとカーソルが残る。外側のタップ（フォーカスを外す）と閉じ方がそろわない。説明も入力するときは、閉じた後に説明欄をタップし直す必要がある |

### 3.4 外側のタップの分かりにくさ

外側のタップで閉じる操作は多くのアプリにある慣習だが、Android の標準の動きではなく、画面に手がかりも出ない。知らない人は気付かない。

ただし、外側のタップは閉じる方法を増やす近道であり、システムの戻る操作は今までどおり使える。気付かない人が閉じられなくなるわけではない。

| 案 | 判断 |
|---|---|
| 説明欄は改行のまま、閉じ方は戻る操作＋外側のタップ＋ボタン操作 | 採用。今できることを減らさずに閉じ方を増やせる |
| 説明欄の Enter も「完了」にして閉じる | 不採用。説明に改行を入れられなくなり、入力できる内容が減る |
| 入力欄に「閉じる」アイコンを付ける | 不採用。Issue の対象外の入力欄の変更になる。必要なら別 Issue にする |

## 4. 実装ステップ

1. この設計メモをレビューする。
2. 登録画面に、余白のタップでフォーカスを外す処理を付ける（3.1）。エミュレーターで余白のタップとスクロールを確かめる。
3. 登録画面の各ボタンの処理にフォーカスを外す処理を足す（3.2）。
4. 登録画面のタイトル欄を「次へ」にする（3.3）。
5. 編集画面に 2〜4 と同じ変更を入れる。入力欄の縦並びには最大の大きさも付ける（3.1）。
6. 5章の確認を行い、結果を記録する。
7. journal を作成し、README、文書一覧、基本設計、要件、ロードマップと関連 ADR を必要に応じて更新する。
8. `/codex:review` を実行し、指摘の採否を決めてから、コミット・push・PR 作成へ進む。

各ステップでは、使う Modifier や仕組みの役割を実際のコードと結び付けて説明し、完成コードを一括で提示しない。

## 5. 確認方法

以下は確認予定であり、実施済みではない。エミュレーターでの確認、Claude によるコード・テストレポートの確認、Codex のレビューを区別して journal へ記録する。

### 手動確認

登録・編集の両画面で行う。

- 余白のタップ：入力欄の間・見出しの横・最後の項目より下の余白をタップすると、キーボードが閉じ、カーソルも消える
- スクロール：キーボード表示中に画面をドラッグしてスクロールしても、キーボードは閉じない（タップと判定されない）
- ラジオボタン：行を押すと選択が変わり、キーボードが閉じる
- 期日：「選択」を押すとキーボードが閉じて日付選択のダイアログが開く。ダイアログを OK・キャンセルで閉じた後に、キーボードが再び開かない。「クリア」を押すと期日が未設定になり、キーボードが閉じる
- 確定ボタン：押すと送信され、キーボードが閉じる
- 入力欄の操作：入力中の欄の中をタップしてカーソルを動かせる。タイトル欄から説明欄をタップして移れる（キーボードは閉じない）
- Enter キー：タイトル欄で Enter の位置のキーが「次へ」の表示になり、押すと説明欄へ移る。説明欄の Enter は改行になる
- 送信中：入力欄・ラジオボタン・ボタンが無効のまま。無効のボタンや行を押しても選択や送信は起きない
- 到達性：キーボードを出したまま、全項目と確定ボタンまでスクロールできる（#65 の確認を再度行う）
- 回帰：[Android 11 の手動回帰テスト](../../test-plans/android/11-todo-regression-testing.md)から、登録・編集の成功と Snackbar、失敗後の入力保持、送信中の戻る制御のケースを再確認する

### 自動テスト

- `testDebugUnitTest` の既存テストが成功する。今回は画面側（Composable）だけの変更で、ViewModel は変えないため、単体テストは追加しない

## 6. 想定される詰まりポイント

- 余白のタップを検出する処理は、縦並びの Modifier の先頭（スクロールより前）に付ける。スクロールより後に付けると、スクロールする内容の中にだけ効き、内容の高さより下の余白で反応しない可能性がある
- 編集画面の縦並びに最大の大きさを付け忘れると、最後の項目より下の余白をタップしても閉じない
- タップの検出（`pointerInput`）の第1引数（`key`）は、値が変わると処理を作り直すための目印である。フォーカスの管理は画面の間で変わらないため `Unit` でよい
- 日付選択のダイアログを閉じた後、フォーカスが入力欄へ戻ってキーボードが再び開く可能性がある。「選択」ボタンの時点でフォーカスを外していれば戻る先がないはずだが、エミュレーターで確かめる
- 送信を始めると入力欄が無効になる。無効になったときにフォーカスがどうなるかは確かめていない。確定ボタンの処理で先にフォーカスを外すため、どちらでも結果は同じになる
- 「次へ」で説明欄へ移るのは、Compose の標準の動きで画面上の次の欄へ進むためである。タイトル欄と説明欄の間に別の操作できる部品を入れると、移る先が変わる
