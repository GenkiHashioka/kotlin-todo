# 詳細設計メモ - Android 08: Todo登録・編集の保存中の戻る操作を制御する

**バージョン**: 0.1
**作成日**: 2026-10-17
**対応Issue**: [#57](https://github.com/GenkiHashioka/kotlin-todo/issues/57)

## 1. 背景

Todo削除では、通信中に詳細を閉じると成功後の一覧通知が失われ得るため、処理中と成功後の自動遷移まで戻る操作を抑止した。登録・編集にも同じ問題がある。画面離脱に伴ってCoroutineがキャンセルされても、Backendの保存を取り消せる保証はない。

削除で実装したcanGoBackとBackHandlerを土台に、登録・編集の状態に合わせて適用する。直近の作業順は#57（戻る制御）、#55（成功フィードバック）、#58（パッケージ整理）とする。

関連文書: [要件](../../requirements.md)、[基本設計](../../architecture.md)、[削除の設計メモ](07-todo-delete.md)、[削除のjournal](../../journal/android/07-todo-delete.md)、[ADR 0023: 成功通知と再取得](../../decisions/0023-navigation-refresh-notification.md)、[ADR 0024: HTTPタイムアウト](../../decisions/0024-http-call-timeout.md)。

## 2. スコープ

### この機能で扱うもの

- 登録・編集の送信中と、成功後の自動遷移まで、Androidの戻るボタン・ジェスチャーによる画面離脱を抑止する。
- 入力中・保存失敗後は戻れる。編集のLoading / LoadErrorでも戻れる。
- 送信中であることをScreenに表示し、操作できない理由を伝える。
- 登録の入力欄・優先度・期日の操作を送信中・登録済みは無効にする案を含める。登録ボタンの無効化にも登録済みを含める。
- 編集では既存の入力・保存ボタンの無効化を維持する。
- 失敗後は入力を保持し、編集・戻る・再送信を受け付ける。
- 既存の成功後の遷移と詳細・一覧の再取得を妨げない。

現状、登録・編集Screenに画面上の戻るボタンは存在しないため、今回は新設しない。将来追加する場合はシステムの戻る操作と同じ可否条件を使う。

### 今回扱わないもの

成功フィードバック（#55）、パッケージ整理（#58）、Backend・API契約変更、新しい共通コンポーネント、DIライブラリ、自動テスト基盤、入力破棄の確認ダイアログ、プロセス再生成時の入力復元。

タイムアウト後の結果確認・再取得・整合回復、重複登録対策、エラー文言の全面的な見直しは含めない。戻る制御で通信断やアプリ終了まで防げるとは扱わない。

## 3. 設計方針

### 3.1 既存状態から戻る可否を計算する

UiStateに新しいフラグを追加せず、Screen内で既存の状態から戻る操作の可否を計算する。

| 画面・状態 | 戻る操作 |
|---|---|
| 登録: isSubmittingもisCreatedもfalse | 許可 |
| 登録: isSubmittingまたはisCreatedがtrue | 抑止 |
| 編集: Loading / LoadError | 許可 |
| 編集: EditingでisSubmittingもisUpdatedもfalse | 許可 |
| 編集: EditingでisSubmittingまたはisUpdatedがtrue | 抑止 |

登録はTodoCreateUiStateから直接判断する。編集は安全なキャストでEditingを取り出し、Editingでなければ戻れる条件とする。hasSubmitError自体は戻る操作を妨げない。

canGoBackはローカルのvalにし、rememberや新しいMutableStateで別管理しない。状態が更新されて再コンポーズされた際に、最新のuiStateから計算し直す。成功済みも条件に含めることで、finallyによるisSubmitting解除から自動遷移までの間も抑止する。

### 3.2 BackHandlerと責務

各Screenの上位でBackHandlerを常に呼び、enabledにcanGoBackの反転を渡す。条件分岐でHandler自体を出し入れせず、有効・無効を状態から切り替える。

戻れない状態ではHandlerがシステムの戻る操作を受け取り、何もせず画面離脱を抑止する。戻れる状態ではHandlerを無効にし、既存のNavigationへ戻る処理を任せる。Handler内からonCreated / onUpdatedやpopBackStackを呼ばない。

| 要素 | 責務・変更方針 |
|---|---|
| TodoCreateScreen / TodoEditScreen | 戻る可否の計算、BackHandler、送信中表示、入力操作の制御 |
| 各UiState | 既存の送信中・成功済み・失敗・入力値を使い、項目は追加しない |
| 各ViewModel | 既存の送信ガード・通信・例外処理・finallyを維持する |
| 各Route / KotlinTodoNavHost | 既存の成功通知・再取得通知・popBackStackを維持する |
| ApiClient | 既存の共有callTimeout 30秒をそのまま使う |

削除成功時と同様、BackHandlerはユーザーの戻る操作を制御し、NavHostからの成功後のpopBackStackは妨げない。画面ごとの短い条件はそのまま持ち、今回だけのために共通化しない。

### 3.3 送信中表示と登録フォームの関連修正

登録・編集とも、isSubmittingがtrueの間だけ送信中のTextをフォーム内へ表示する。文言はstrings.xmlで管理し、例えば「送信中…」を両画面で共有する。成功メッセージは#55の範囲とする。編集中の画面をLoadingへ切り替えず、入力を保持したまま進行状態を表示する。

現在の編集フォームは送信中・更新済みに入力操作を無効にしている。一方、登録フォームは送信ボタンだけを無効にしており、送信後もタイトル・説明・優先度・期日を変更できる。送信内容は開始時に確定しているため、後から入力した値が保存されず、成功時に失われる可能性がある。

関連修正案として、登録フォームの入力欄、優先度、期日の選択・解除も送信中・登録済みは無効にする。登録ボタンにもisCreatedの条件を追加し、既存のViewModelのガードと揃える。画面の無効化は操作への案内、ViewModelのガードは処理の開始防止として両方を維持する。

### 3.4 失敗後の操作復帰と既知の制約

通常の失敗はhasSubmitErrorで表示し、finallyでisSubmittingをfalseにする既存処理を使う。成功済みはfalseのままなのでcanGoBackもtrueになり、入力を保持したまま戻る・再編集・再送信ができる。CancellationExceptionの再スローは維持する。

長時間のHTTP呼び出しにはADR 0024の共有タイムアウトを使う。ViewModelへのwithTimeoutや別のタイムアウト設定は追加しない。タイムアウトしてもBackendで保存済みの場合はあり、登録の再送信で重複する可能性も残る。操作復帰と保存結果の確定は別の問題である。

### 3.5 ADRの扱い

成功後の再取得通知はADR 0023、共有HTTPタイムアウトはADR 0024を継続する。今回は削除で採用した画面の操作制御を既存状態へ適用するため、新規ADRは予定しない。実装中に共通方針の変更が必要になった場合は追加要否を見直す。

## 4. 実装ステップ

1. Windows側で修正用ブランチを作成し、この設計メモをレビューする。
2. 登録ScreenでcanGoBackを計算し、BackHandlerを追加する。
3. 編集ScreenでLoading / LoadErrorも考慮したcanGoBackとBackHandlerを追加する。
4. 送信中表示と、登録フォームの入力操作・登録済みのボタン制御を追加する。
5. 送信中・失敗後・成功後の遷移を手動確認する。
6. 対応するjournalを作成し、README、文書一覧、基本設計、要件、ロードマップ、関連ADRを確認して影響のある箇所を更新する。
7. 開発者がコード・文書をレビューし、コミット・push・PR作成を行う。

実装は開発者が一歩ずつ行い、Codexは目的・仕組みの説明とレビューを担当する。

## 5. 確認方法

以下は実装後の確認予定であり、確認済みではない。Android Studioでのビルドと手動確認、Codexの静的レビューを区別してjournalへ記録する。自動テスト基盤は今回追加しない。

- 登録・編集とも送信前は、Androidの戻る操作で元の画面へ戻れる。
- 編集の初期取得中・取得失敗でも戻れる。
- 送信中は進行表示が出て、戻るボタン・ジェスチャーで画面を離れない。
- 登録の送信中はタイトル・説明・優先度・期日を変更できず、追加送信できない。編集の既存の入力制御も維持される。
- 保存成功後は自動で戻り、登録は一覧、編集は詳細と一覧を再取得する。
- 保存失敗では入力が残り、進行表示が消えて、戻る・再編集・再送信ができる。
- 続けて登録・編集した場合も戻る制御と成功通知が機能する。
- 既存の削除中の戻る制御・成功後の一覧更新を壊していない。

送信が速い場合はViewModelに一時的なdelayを置いて操作制御を確認できるが、これはHTTPタイムアウトの検証ではない。タイムアウトを再検証する場合はBackendの応答遅延と短いcallTimeoutを一時的に使い、操作復帰を確認する。確認用データを使い、終了後はdelay・不要なimport・設定変更を戻す。結果不明後の整合回復を確認済みとは扱わない。

## 6. 想定される詰まりポイント

- 編集の条件をEditingだけに限定すると、Loading / LoadErrorでも戻れなくなる。状態ごとの可否を表で確認する。
- BackHandlerのenabledは戻る許可ではなくHandlerの有効化である。戻れないときに有効にする。
- 成功済みの条件がないと、finallyの解除後にユーザーが戻る操作を実行できる隙間ができる。
- canGoBackをrememberした初期値だけで保持すると、状態変化に追従しない。既存uiStateから毎回計算する。
- Screenの操作制御だけで二重送信を保証しない。既存のViewModelのガードを維持する。
- ユーザーの戻る操作の抑止と、NavHostの成功後の自動遷移を区別する。
- 画面離脱を抑止しても、アプリ終了・通信断・タイムアウト後のBackend処理完了は防げない。
