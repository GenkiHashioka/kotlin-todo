# 詳細設計メモ - Android 06: Todoを編集し、詳細・一覧へ反映する

**バージョン**: 0.1
**作成日**: 2026-10-04
**対応Issue**: [#52](https://github.com/GenkiHashioka/kotlin-todo/issues/52)

## 1. 背景

一覧・詳細・登録に続き、既存Todoの内容と進捗をAndroidから更新する。登録時は未着手として作成し、編集で進行中・完了へ変更できるようにする。

登録はこれから行うTodoを未着手で作る操作、編集は既存の内容と進捗を変更する操作とする。

関連文書: [要件](../../requirements.md)、[基本設計](../../architecture.md)、[ADR 0005: 全項目を送信するPUT](../../decisions/0005-update-uses-put-not-patch.md)、[登録機能の設計](05-todo-create.md)。

## 2. スコープ

### この機能で扱うもの

- 詳細の取得成功時に編集画面へ進む操作を追加する。
- Todo IDをNavigation引数で渡し、編集画面でGET /todos/{id}から現在の値を取得する。
- タイトル、説明、任意の期日、優先度、ステータスを編集する。
- ステータスはNOT_STARTED / IN_PROGRESS / DONEを選べる。初期値には既存のステータスを使う。
- categoryIdは取得したcategory?.idを保持し、選択UIは追加しない。
- PUT /todos/{id}で更新し、取得失敗・保存失敗・送信中を扱う。
- 成功後は元の詳細へ戻り、詳細と一覧の両方を最新データへ更新する。
- 保存せず戻る操作では更新リクエストも更新通知も送らない。

### 今回扱わないもの

カテゴリ選択、Todo削除、Backend拡張、DIライブラリ、登録と編集の全面的な共通化、確認ダイアログ、プロセス再生成時の入力復元、競合更新の検出、自動テスト基盤の導入。レイアウトの洗練は別途扱う。

## 3. 設計方針

### 3.1 編集対象の取得と初期値

TodoEditDestinationにはtodoIdだけを渡す。詳細画面のDTO全体を渡す方法もあるが、編集画面自身がIDから取得する構成を採用する。既存の詳細取得と同じ責務を使え、画面間でデータのコピーを受け渡す必要がない。代わりに画面を開く際の追加通信とLoading / 取得失敗の表示が必要になる。

ViewModelはSavedStateHandleからNavigation引数を読む。入力欄は取得成功後に表示し、その時点で一度だけ現在値から初期化する。再コンポーズのたびに初期値を設定してユーザー入力を上書きしない。

### 3.2 状態と責務

初期取得と保存の失敗を区別する。状態はLoading、LoadError、Editingの3種類を持つsealed interfaceを案とする。Editingにはタイトル、説明、期日（`LocalDate?`）、優先度、現在のステータス、保持するcategoryId、isSubmitting、hasSubmitError、isUpdatedを持たせる。

取得前や取得失敗では入力・保存を受け付けない。LoadErrorの再試行は取得処理を再開する。保存失敗時はEditingの入力を保持し、同じ内容を再送信できるようにする。

| 要素 | 責務 |
|---|---|
| TodoEditScreen | 状態に応じた取得中・取得失敗・入力フォーム・保存失敗の描画とcallback通知 |
| TodoEditRoute | StateFlowの監視、入力・再試行・保存callbackの接続、成功時の副作用 |
| TodoEditViewModel | 初期取得、入力状態、保存処理と結果の管理 |
| TodoEditViewModelFactory | RepositoryとNavigationに対応したSavedStateHandleを渡す |
| TodoRepository / TodoApi | PUTの更新処理を提供する |
| KotlinTodoNavHost | 編集への遷移、戻る操作、詳細と一覧への更新通知 |

### 3.3 PUTと編集しない項目の保持

既存のADR 0005に従い、変更後の全項目を送信する。TodoUpdateRequestをAndroid側へ追加する。IDはURLパスへ渡し、本文にはタイトル、説明、期日、優先度、ステータス、categoryIdを含める。

登録用Requestを使い回さず更新契約を別DTOにする。現在のフィールドが同じでも用途とAPI契約を区別するためである。説明は空白入力をnullへ、期日は日付文字列またはnullへ変換する。ステータスをNOT_STARTEDへ固定したり、カテゴリを常にnullにしたりしない。

選択可能なステータスの順序を強制するルールは今回追加しない。未着手から直接完了へ変更することや、完了から戻すことも許容する。

### 3.4 保存処理

通常のViewModel関数からviewModelScope.launchでRepositoryのsuspend関数を呼ぶ。送信前に入力と状態を確認し、空白タイトル・送信中・更新済みの場合は保存を拒否する。送信内容は開始時の入力から確定する。

開始時に前回の保存エラーを消して送信中にする。通常の例外は保存失敗状態へ、CancellationExceptionは再スローし、finallyで送信中を解除する。成功時のみisUpdatedをtrueにする。失敗文言はScreenがstrings.xmlから取得する。

### 3.5 成功後の詳細・一覧更新

RouteはLaunchedEffectで更新成功を受け取り、NavHostのcallbackを呼ぶ。NavHostは戻り先の詳細と、Back Stackに保持された一覧の両方へ再取得通知を保存してからpopBackStackする。

詳細側はtodo_detail_refresh_required、一覧側は既存のtodo_list_refresh_requiredを使う。各画面が通知を受け付けたらrefresh()を呼び、通知をfalseへ戻す。通知の解除は再取得開始を意味し、通信完了を意味しない。

一覧と詳細はViewModelが保持されるため、戻るだけではinitの取得は再実行されない。詳細だけ更新すると一覧のタイトルが古いままになるため、両方を更新対象とする。再取得失敗時はそれぞれの既存のError表示と再試行で扱う。

```text
一覧 → 詳細 → 編集（IDから初期取得）
              ↓ PUT成功
       詳細と一覧へ更新通知を保存
              ↓ 編集を取り除く
           詳細を再取得
              ↓ 一覧へ戻る
           一覧も最新値を表示
```

更新後のDTOを手動で各画面へ反映する方法もあるが、今回もAPIから再取得する方針を使う。Repositoryの共有キャッシュは現状の要件では追加しない。

### 3.6 ADRの扱い

PUT方式はADR 0005を継続して使い、新規ADRで重複させない。編集項目やフォームの初期値はこの機能の設計メモへ記録する。画面間の更新通知方式は登録・編集で共通する判断のため、実装を通じた制約の確認後、PR準備時にADRへの切り出しを検討する。

## 4. 実装ステップ

1. Issueを起票し、編集用ブランチとこの設計メモのレビューを済ませる。
2. TodoUpdateRequest、TodoApiのPUT、Repositoryの更新処理を追加する。
3. 編集Destination、Factory、初期取得と状態を持つViewModelを追加する。
4. 詳細の編集操作からIDを渡し、取得した現在値をフォームへ表示する。
5. 入力変更、ステータス選択、保存失敗、送信中と再送信ガードを接続する。
6. 成功時の詳細・一覧への通知と戻る処理を接続する。
7. 手動確認、理解確認、journalと関連文書の必要な更新、ADRの追加要否確認を行う。

各ステップを小さく実装・レビューし、完成コードを一度に提示しない。

## 5. 確認方法

Android Studioでビルド・実行する。以下は確認予定で、現時点で実施済みではない。

- 既存値が入力の初期値になる。進行中・完了のTodoも初期値を未着手へ戻さない。
- タイトル、説明、期日、優先度、ステータスを変更して保存できる。
- 説明・期日の解除とcategoryIdの保持を確認する。
- 初期取得の失敗ではフォームを保存できず、再試行できる。
- 保存失敗では入力を保持し、エラー表示と再送信ができる。
- 空白タイトル、送信中、更新済みの追加送信を拒否する。
- 成功時に詳細へ戻り、変更値が表示される。さらに一覧へ戻るとタイトルも更新されている。
- 続けて編集した場合も再取得通知が機能する。
- 保存せず戻った場合、変更がBackendへ反映されない。

自動テスト基盤は今回の対象外。必要な検証方法は実装レビューで見直す。

## 6. 想定される詰まりポイント

- nullable項目を送らないことと既存値の保持は同じではない。PUT契約ではnullが値の解除になる。
- 編集画面の初期値設定を描画処理へ置くと入力を上書きする。取得成功時にViewModelで設定する。
- 初期取得失敗と保存失敗では、入力を保持する必要性が異なる。
- 保存成功後は詳細だけでなく一覧も更新する。previousBackStackEntryは今回一覧ではなく詳細を指す。
- 画面間の更新通知と画面の戻る操作は別処理であり、両方必要。
- 編集画面を破棄しても保存先の処理完了を取り消せる保証はない。レスポンス喪失・競合更新への対策は別課題として扱う。
