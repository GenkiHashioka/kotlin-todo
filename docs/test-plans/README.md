# テスト設計（test-plans）

テストを実施する前に、何をどの条件で確認するかを決める文書を配置する。実装方法を決めるdesign-notes、実際の結果を残すtestingと分ける。

## 文書の使い分け

| 配置 | 記載内容 |
|---|---|
| [design-notes](../design-notes/README.md) | 責務・構成・処理方式。自動テストコードのFakeやCoroutine制御の設計も含む |
| test-plans | 対象・観点・前提条件・手順・期待結果 |
| [testing](../testing/README.md) | 実施環境・実際の結果・証拠・判定 |
| [journal](../journal/) | 学び・判断・計画との差分・残る課題 |

小さな変更ごとに別のテスト設計を必須にはしない。実装設計の検証節で十分ならそこへ書く。機能横断の回帰テストなど、ケースを詳しく整理する必要がある場合に本ディレクトリへ分ける。実装設計とテスト設計を両方作る場合は、内容を重複させず相互にリンクする。

## 配置と命名

- Android: `android/{連番2桁}-{topic-kebab-case}.md`
- Backend: `backend/phase-{番号}-{topic-kebab-case}.md`
- Trackの連番・topicは対応するjournalと揃える。実装設計・テスト設計のどちらを主文書とするかは作業の目的で決め、空の対応文書は作らない。
- 今回の例: [Android 11: Todo機能の回帰テスト](android/11-todo-regression-testing.md)。

## 記載する内容

1. 背景・確認の目的・対応Issue。
2. 対象と対象外、関連する要件・実装設計。
3. 実施環境、テストデータ、失敗・待機状態の再現方法。
4. ケースIDごとの前提条件・操作手順・期待結果。
5. 実施順序、役割分担、結果の記録先、終了条件。
6. 想定される詰まりポイント、既知の制約、確認用変更の復旧方法。

開発者がレビューしてから実施する。実施中に再現方法や条件を変える場合は、その理由と変更内容を明記し、実際の条件を実施記録にも残す。計画の期待結果を、観察した現行コードへ無条件に合わせない。仕様と結果が異なる場合は、不具合か仕様の見直しかを判断する。

実施後は計画を当時の記録として維持し、実施結果をtesting、学びをjournalへ記録する。過去のdesign-notesに含まれる検証節を一括移動する運用にはしない。
