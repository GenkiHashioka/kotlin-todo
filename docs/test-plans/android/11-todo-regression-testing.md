# テスト設計 - Android 11: Todo機能の回帰テストを設計・実施する

**バージョン**: 0.2（2026-10-18: C01実施前に応答遅延の再現条件を具体化）
**作成日**: 2026-10-18
**対応Issue**: [#62](https://github.com/GenkiHashioka/kotlin-todo/issues/62)

## 1. 背景

Todo CRUD、処理中の操作制御、成功フィードバック、画面別パッケージ整理が揃った。機能追加ごとの手動確認に加え、画面をまたぐ操作と異常系を同じ観点で確認する。

回帰テストは、変更後も既存の振る舞いが維持されているかを確認するもの。今回の狙いは、期待する仕様を先に定め、実際の結果と比較し、未確認の範囲や既知の制約を区別することである。手動確認結果から、自動化の最初の対象も選ぶ。

関連: [要件](../../requirements.md)、[基本設計](../../architecture.md)、[ロードマップ](../../roadmap.md)、[ADR 0023](../../decisions/0023-navigation-refresh-notification.md)、[ADR 0024](../../decisions/0024-http-call-timeout.md)、[Android 10のjournal](../../journal/android/10-todo-ui-packages.md)。

## 2. スコープ

### 今回扱うもの

- 既存のCRUD・取得失敗・保存失敗・操作制御・成功通知について、前提条件・手順・期待結果を整理する。
- 開発者がAndroid StudioとローカルBackendで手動テストを行い、結果を記録する。
- 不具合と仕様上の制約を区別し、必要な修正・後続Issueを整理する。
- 自動化候補を比較し、最初の自動テスト実装用の後続Issueを起票する。

### 今回扱わないもの

すべてのケースの一括自動化、新しいDIライブラリ、テスト用の全面的なアーキテクチャ変更、Backendのテスト戦略再構築、CI整備、性能・負荷試験、全端末・全OSの組み合わせ、通知や入力のプロセス再生成対応。

既知の結果不明時の整合回復・並び順・タップ範囲の改善は本Issueで一括実装しない。新たに見つかった問題も、内容を記録して修正範囲を判断する。

## 3. 設計方針

### 3.1 期待結果と実施結果を分ける

本書は確認予定を表す。過去のjournalに動作確認報告があっても、今回の実施結果を自動的に合格へしない。

実行開始時にdocs/testing/android/todo-regression-results.mdを用意し、次を記録する。

- 実施日、Windows側のブランチとコミット、端末またはEmulator、OS、アプリのビルド条件。
- Backendのコミット・起動状態、使ったテストデータのID、再現のための一時変更。
- ケースID、実際に行った操作、実際の結果、判定、必要な証拠と関連Issue。

判定は未実施 / 合格 / 不合格 / 実施不可とする。実施不可には理由を記録する。既知の制約は注記し、要件を満たさない動作を単に合格へ置き換えない。期待結果を満たすと確認できたケースだけを合格にする。

Codexは静的レビュー・文書整理を担当し、端末操作やBackendの実行確認は開発者の報告として記録する。実施結果をまとめた後にjournal 11を作成する。

### 3.2 実行環境とテストデータ

AndroidはWindows側、BackendとPostgreSQLはWSL側という現在の構成を使う。通常動作を確認してから、通信失敗・処理中・結果不明の順に進める。全ケースを一度に実施せず、小さなグループごとに結果をレビューする。

タイトルに「REG62-」などの識別子を付け、作成したTodoのIDを記録する。通常データ、任意項目なし、日付あり、カテゴリ付きの編集対象を用意する。カテゴリ付きデータは既存のローカルAPIまたはDB操作で準備し、具体的な手順とIDを実施前に確認する。

Emptyと最後の1件の確認には他のTodoがない状態が必要になる。既存データを一括削除せず、空にできる開発用データの範囲を確認してから実施する。準備できない場合は実施不可として理由を残す。データの準備・後片付けの操作をテスト結果と混同しない。

保存・削除が実際に行われたかは、画面の結果に加え、必要に応じてGET /todos/{id}や一覧APIで確認する。一覧の並び順は未定義なので、行番号ではなくID・タイトルで対象を確認する。

### 3.3 失敗・処理中の再現

| 条件 | 再現方法 | 何を確認できるか・限界 |
|---|---|---|
| 通常の通信失敗 | 画面に必要な値を取得した後、ローカルBackendを停止して操作し、再起動して再試行する | 接続できない場合の失敗表示・入力保持・復帰。HTTP 4xx / 5xxや応答喪失とは区別する |
| 処理中・Loading | 検証用のローカル変更として、対象Repository関数のAPI呼び出し直前にsuspendのdelayを数秒入れる | 処理中の状態を観察するための待機。HTTPタイムアウトの検証にはならない |
| 保存成功後の再取得だけ失敗 | 対象GETだけを失敗させる一時的な仕掛けを別途レビューしてから使う | 成功通知と再取得Errorが両立すること。全通信を止めて保存自体まで失敗させない |
| Backendで削除済みだが応答がタイムアウト | 使い捨ての削除対象で、削除処理完了後・応答前に35秒待機する | 結果不明の観察。個別タイムアウトが先に発生し得るため、常に30秒を待つと期待しない |

delayはThread.sleepにせず、UIスレッドを塞がない待機を使う。対象の関数だけを変え、通常データで通信できる状態を先に確認する。失敗後の操作復帰を確認する場合は、同じ待機を入れたままBackendを停止して実行できる。

保存・削除のタイムアウト後は、Backendの実データを確認するまで安易に再送しない。クライアントの失敗表示がBackendでの未保存・未削除を意味するわけではない。

一時変更の具体的な差分は、そのグループを実行する前に開発者と確認する。特にBackend側の遅延とGETだけを失敗させる方法は、対象・待機条件・復旧方法を確定してから使う。結果には一時変更を明記し、通常構成の検証と区別する。最後に一時コードを取り除き、共有callTimeoutが30秒のままであることと、通常ビルド・起動・主要経路を再確認する。

### 3.4 手動テストケース

同じ行に複数の入力・画面がある場合も、実施結果では枝番を付けて個別に判定する。以下は実施順の目安。

#### A. 通常操作・入力・画面連携

| ID | 前提条件と操作 | 期待結果 |
|---|---|---|
| A01 | Todoがある状態で起動し、一覧から対象を開き、詳細から戻る | 一覧と対象IDの詳細を表示し、戻れる |
| A02 | 一覧が空の状態で起動する | Empty表示となり、登録へ進める |
| A03 | 登録画面を開き、空文字・空白のみのタイトルを入力する | 送信不可。優先度の初期値はLOW |
| A04 | タイトルだけで登録し、一覧と詳細・APIを確認する | 1件登録され、一覧更新と登録Snackbar。説明・期日は未設定、優先度LOW、ステータスNOT_STARTED、categoryIdはnull |
| A05 | 説明・期日・優先度を指定して登録する | 選択した値が保存・再表示される。説明が空白のみの場合はnullになる |
| A06 | 登録で期日選択を確定・変更・解除する。別途カレンダーをキャンセルする | 確定した日付を反映し、解除すると未設定。キャンセルで元の入力値を変えない |
| A07 | 登録画面へ入力し、送信せず戻る | 登録も成功通知も発生しない。再度開くと新規登録の初期値になる |
| A08 | 任意項目のあるTodoを編集し、値を変更して保存する | 初期値が取得値と一致し、保存後の詳細と一覧に更新を反映。更新Snackbarは保存後に表示され、一覧へ戻るだけでは再表示しない |
| A09 | 編集で説明を空白へ、期日を解除して保存する。カレンダーのキャンセルも別途確認する | 説明・期日はnullとして保存。カレンダーキャンセルでは入力値を変えない |
| A10 | 編集のタイトルを空文字・空白のみにする | 保存できない |
| A11 | ステータスをNOT_STARTED → IN_PROGRESS → DONEへ順に保存し、DONEからNOT_STARTEDへも戻す | 各保存結果が再表示され、遷移順序を制限しない |
| A12 | カテゴリ付きTodoを編集し、カテゴリ以外を変更して保存する | categoryIdが維持され、カテゴリ選択UIは増えない |
| A13 | 編集で入力を変え、保存せず戻る | 保存・成功通知が発生せず、改めて開くと保存済みの値を取得する |
| A14 | 詳細で削除ダイアログを開き、キャンセルボタン・ダイアログ外のタップまたは戻る操作で閉じる | 対象は削除されず、詳細を維持。成功Snackbarは出ない |
| A15 | 詳細から削除を確定する。最後の1件の場合も別途実施する | 対象が消え、一覧へ戻って再取得し、削除Snackbar。0件ならEmpty |
| A16 | 登録・編集・削除後、Snackbarが消えるのを待ち、画面を再訪する | 短時間で消え、再訪だけで同じ成功通知が再表示されない |
| A17 | Snackbar表示中に次の操作を成功させる | 対応する成功メッセージが順番に表示される |

#### B. 通信失敗・復旧・処理中

| ID | 前提条件と操作 | 期待結果 |
|---|---|---|
| B01 | Backend停止中に一覧・詳細・編集の初期取得を行う。復旧後に各画面で再試行する | 各Error / LoadErrorから再取得でき、取得失敗時にも戻れる |
| B02 | 登録へ入力後にBackendを停止し送信する。復旧後に同じ入力で送信する | 失敗表示・入力保持・再編集と戻る操作の復帰、成功通知なし。復旧後に登録可能 |
| B03 | 編集を取得後、入力を変更してBackend停止中に保存する。復旧後に再送する | 初期取得エラーと保存エラーを区別し、入力保持・操作復帰。復旧後に保存可能 |
| B04 | 詳細を取得後、Backend停止中に削除を確定する。復旧後に再試行する | 詳細を保持して削除失敗を表示し、戻る・編集・削除を再開できる。失敗時の成功通知なし |
| B05 | 取得前に一時待機を入れ、一覧・詳細・編集を開く | Loadingを表示。詳細・編集の取得中は戻れる |
| B06 | 登録と編集の送信前待機中に、入力・優先度・期日選択／解除・追加送信・システムの戻る操作を試す。編集ではステータスも試す | 「送信中…」を表示し、各操作を抑止。完了すると正常に戻って更新。UIの連打で対象の保存が重複しない |
| B07 | 削除の待機中に、戻るボタン・システムの戻る・編集・追加削除を試す | 「削除中…」を表示し各操作を抑止。完了すると一覧へ戻る |
| B08 | B06 / B07の待機を残してBackend停止中に実行する | 待機中は操作を抑止し、失敗後は進行表示が消えて操作復帰する |
| B09 | 保存・削除は成功させ、戻り先のGETだけを失敗させる。GETを復旧して再試行する | 操作の成功Snackbarと再取得Errorが併存し得る。取得の再試行で保存・削除や成功通知を繰り返さない |

成功フラグが立ってから自動遷移するまでの短い区間と、ViewModelを直接連続呼び出しした場合のガードは、手動操作だけでは確実に分離して確認しにくい。B06 / B07の手動結果からそれらの全条件まで検証済みとはせず、自動化候補に残す。

#### C. 既知の制約の観察

| ID | 前提条件と操作 | 期待結果・扱い |
|---|---|---|
| C01 | 使い捨てTodoをBackendで削除した後、HTTP応答前に35秒待機させ、Androidのタイムアウト後にDBとAPIで実データを確認する | Androidは待機を解除して失敗を表示し、操作復帰する。一方、Backendでは削除済みとなる。実際のタイムアウト種別・経過時間・削除結果を記録し、整合回復未対応として扱う |

C01の具体化では、削除前の遅延案から、DB削除完了後の応答遅延へ変更した。クライアント切断によるキャンセルで削除自体が実行されなくなる可能性と分け、削除済みなのにクライアントでは失敗となる条件を作るためである。タイムアウト後に新たに削除が完了する順序までは、この試験では検証しない。Android 07で観察した後からの削除完了とは区別する。Androidの30秒callTimeoutは変更しない。

C01は本番設定のcallTimeoutが必ず発火することを証明する試験ではない。再現方法が確定しない場合は実施不可とし、Android 07の過去の観察記録と今回の結果を区別する。画面回転・プロセス再生成時の通知や入力の復元は今回は対象外とする。

### 3.5 自動化の候補と最初の対象案

現在はJUnitとCompose UIテストの依存設定があるが、src/test / src/androidTestのテストソースはない。依存設定があることと、テストを実行済みであることを区別する。

| 対象 | 自動化で確認したいこと | 準備・判断 |
|---|---|---|
| 一覧ViewModel | LoadingからSuccess / Empty / Error、retry / refresh | 最初の候補。ID引数や書き込みがなく、StateFlowとCoroutineテストを小さく学べる |
| 登録・編集・削除ViewModel | 入力変換、失敗保持、再送信ガード、キャンセル | 次候補。実行順・完了待ちと呼び出し回数を制御して確認する |
| Repository / TodoApi | JSON・HTTP契約やエラーの伝播 | 現在のRepositoryは委譲が中心。委譲だけを写したテストより、通信契約を検証する必要性に応じて検討する |
| Compose Screen | 状態別表示、操作無効、callback | 画面に状態を渡すテストで確認できる候補。端末テストの環境・操作の学習が必要 |
| Navigation全体 | 戻り先の再取得とSnackbar | 複数要素が関わるため、最初から全件をUI自動テストにしない |

最初は一覧ViewModel案を推すが、手動テストの結果と開発者のレビューで確定する。既存のTodoApiはinterfaceなので、テスト用実装から取得結果や例外を返し、実際のTodoRepositoryへ渡す構成を候補にする。Repositoryを継承可能にする変更やDIライブラリは、この目的だけでは必要ない。

一覧ViewModelのテストでは、StateFlowの値とテスト用Coroutineの実行順を制御する。ローカルJVM上ではMain dispatcherの置き換えが必要になるため、後続Issueでkotlinx-coroutines-testとrunTestなどを学ぶ。依存バージョンは導入時点で互換性を確認し、今回は追加しない。

参考: [Coroutineテストの公式ガイド](https://developer.android.com/kotlin/coroutines/test)、[テスト用代替実装の公式説明](https://developer.android.com/training/testing/fundamentals/test-doubles)。

### 3.6 ADRと文書

今回は既存仕様の検証計画であり、新しい本番アーキテクチャを採用しないため新規ADRは原則不要。自動テストの構成は、後続実装の設計時に改めて判断する。

テスト結果とjournalを残し、README・文書一覧・基本設計・要件・ロードマップについて確認状況と残る制約を反映する。テストで仕様との矛盾を見つけた場合は、現行コードを正解として期待結果を書き換えず、仕様または実装のどちらを直すか相談する。

## 4. 実施ステップ

1. test/android-todo-regressionブランチを作成し、本設計をレビューする。
2. 実施記録を作成し、環境とテストデータを準備する。
3. Aの通常操作を小さなグループで実施し、結果をレビューする。
4. 再現方法と一時変更を確認したうえで、Bの失敗・復旧・操作制御を実施する。
5. Cの結果不明を観察し、制約と未実施を記録する。
6. 発見事項と自動化候補を見直し、後続Issueの本文を作成して開発者が起票する。
7. 検証用変更を除去し、通常構成でビルド・起動・主要経路を確認する。
8. journalと関連文書を更新し、開発者がレビュー・コミット・push・PR作成を行う。

## 5. 完了の確認方法

- ケースごとに結果と判定、実施不可・未実施の理由を追える。
- 不具合を記録し、対応済みか後続Issueへ分けたかを明示する。
- 自動化の最初の対象と選定理由を合意し、実装用の後続Issueを起票する。
- 実施結果、学び、静的確認と手動確認の区別をjournalに残す。
- 確認用コードが残っておらず、git diff --checkと文書リンク確認が通る。

## 6. 想定される詰まりポイント

- 操作が速く処理中を確認できない。観察用待機を使い、通信タイムアウトとは区別する。
- 実施条件が違うのに同じケースを合格とまとめる。各画面・条件を枝番で記録する。
- データの並び替えを保存失敗と誤認する。IDと値で判断する。
- 失敗後に再送して重複を作る。接続不能と結果不明を区別し、結果不明なら実データを先に確認する。
- 手動連打だけでViewModelのガードも保証したと考える。UI無効化と内部ガードは別の確認として扱う。
- 過去の確認結果を今回の合格として転記する。対象コミット・実行条件と今回の結果を記録する。
- 確認用コードを通常実装として残す。一時変更を都度確認し、終了時に除去して通常構成で再確認する。
